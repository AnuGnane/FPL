# v19 — the surface and the week (programme)

> **For agentic workers:** this is a *programme*, not a task plan. Each
> sub-cycle below (v19a … v19h) gets its own spec, its own branch and its
> own gate, run the house way: spec with the gate written first →
> implementer briefs as scratchpad files → opus implementer per brief, one
> committing agent at a time → the orchestrator reviews every diff → gates
> run by the orchestrator → screenshots approved → ff-merge → push →
> security ritual → docs → the tracker. Paste the **Prompt** block of the
> sub-cycle you are starting into a fresh chat if the session rolls over.

**Goal:** make the site tell the weekly reader what they look for first
(the deadline, whether the machine is alive, what changed), close the
Friday loop on one hub, design the phone, let the reader compare and act,
ship the model work that needs no replay, and leave the code and docs
tidier, without changing a number the advice serves.

**Design:** `docs/superpowers/specs/2026-09-15-v19-programme-design.md`,
approved by the user 2026-09-15 with all eleven rulings as proposed. Read
§1 before a sub-cycle's section here.

**Research:** `docs/superpowers/research/2026-09-15-v19-research-frontend.md`,
`-backend.md`, `-product.md`.

**Tech stack:** unchanged. Python 3.12 `src/gaffer`, pytest 9, ruff; React
18 + TS + Tailwind v4 + vitest + ESLint in `frontend/`. Nothing new.

**Usage (ruling 10):** Fable orchestrates, reviews and runs gates; opus
implementers; sonnet for mechanical sweeps; no reviewer agents; at most
three briefs per sub-cycle.

**Tracker:** `docs/superpowers/plans/2026-09-15-v19-tracker.md`.

## 2. What every sub-cycle does the same way

Everything in `plans/2026-09-12-v18-polish-programme.md` §2 applies
unchanged: mutation-test every new rail, one committing agent at a time,
a "no diff" needs a same-code control, every brief carries a "where your
judgement is wanted" section. With three additions:

1. **Briefs are files.** Each implementer brief is written to the
   scratchpad and names: the branch, the files it may touch, the files it
   may not (CLAUDE.md's orchestrator-only list), the tests to add with
   their sentence names, the exact verification commands, the commit
   subject, the trailers, and a report format under twenty lines.
2. **Phone and tablet shots from v19c on.** `frontend/scripts/shots.sh
   <stage>` takes 1400-wide pairs for the byte comparison and, once v19c
   has added them, 375 and 820 shots that the user approves by eye
   (ruling 7).
3. **Input timing is declared.** v19a's field-bank change and v19b's price
   step are the two changes that alter *when* an input is read (rulings 4
   and 5). Each gate includes a real before/after read pasted into the
   spec's outcome.

**Gates in this programme are of three kinds.**

- *Golden* (v19a, v19b, v19e, v19f, v19g, v19h): `.venv/bin/pytest -q -rs
  tests/test_golden_board.py tests/test_pipeline.py` → **58 passed, 0
  skipped**, about eighteen minutes, fixture untouched unless the spec
  declares a change.
- *Surface* (every sub-cycle that touches `frontend/`): `cd frontend &&
  npm run check` green with no `Errors` line; the fetch rails
  `src/hubs/*.fetches.test.tsx` unchanged unless named; `shots.sh
  v19<letter>-before` on `main` then `-after` on the branch, same time,
  both themes; byte-identical for every hub the spec does not name.
- *Rule* (v19g's readings, v19h's counts): the named commands with their
  exact expected output, pasted into the spec's outcome.

Always: the inner loop `.venv/bin/pytest -q -m "not slow and not golden"`
and `uvx ruff check src tests` before any commit is reviewed.

**Pins.** Routes 51 → 52 (v19e) → 53 (v19f); job kinds 12 throughout;
`Config` 62 → 61 (v19h). Each move in its own commit to the file that
holds the pin (`tests/test_v11_degradation.py`,
`tests/test_v13_degradation.py`); the meta-rail keeps the homes.

**Security.** The odds key by name only, `[odds] api_key`. Subagents never
open `config.toml`. The ritual before every push.

## 4. When a sub-cycle fails its gate

The v17 rule holds: the branch does not merge; the spec's §Outcome records
the failure with the numbers; the tracker's hand-off note says what was
learned; the next sub-cycle starts from the last merged hash. A screenshot
diff on an unnamed hub is a failure until a same-time control explains it.
