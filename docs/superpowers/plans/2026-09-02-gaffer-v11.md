# Gaffer v11 Implementation Plan — the UI trio

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** three views that render numbers the tree already computes — a GW-by-GW planner board, a comparison that shows the model's reasoning, and a season dashboard that fills as gameweeks grade. Nothing on the training path moves, nothing on the decision path moves, and **no view calls a solver**.

**Architecture:** three workstreams and a close-out, and the honest shape of them is not the shape the spec suggests. Every workstream came back *smaller on the server* than the spec expects and *larger in exactly one place* the spec does not name.

- **W1 (§F1, Tasks 1, 5, 6)** is the planner board. Smaller, because `/api/plan/{gw}` already serves the whole horizon — buys and sells with prices, hits, hit cost, chip, expected points — and `/api/prices/movers` already serves the price-change warnings and **is fetched by nothing** (A9). Larger, because **the plan carries no bank at all** (A8): `plan_by_gw` was written with four keys and none of them is money, so the bank trajectory the spec asks for is derived at `plan.py` from `SolveState.bank`, with a rule about what an unpriced move does to every week after it. And the "try changes" handoff is not a deep link — there is no such thing in this app (A6, A7): it is Planning's hoisted `whatif` state plus a Radix `Tabs.Root` that has to stop being uncontrolled.
- **W2 (§F2, Tasks 2, 7, 8)** is the comparison deepen, and it is the workstream the spec most overestimates. `ComparePanel` **already fetches `/api/components/{gw}` and `/api/fixtures/matrix?from={gw}&n=6`**, already draws an EP-component chart off the first, already draws next-six chips off the second, and already prints all three ownership numbers (A1). The set-piece and pen-taker flags are already on `PlayerRow`. The one genuine server gap in the whole workstream is the field EO's **standard error** (A2) — four characters of dict access at `players.py:170` that nobody has ever written down. Everything else is a re-pivot of bytes already on the client.
- **W3 (§F3, Tasks 3, 4, 9, 10)** is the season dashboard. `season_summary` is **already served**, on `GET /api/review`, and carries the lanes with their graded counters, the per-GW accuracy series (which nothing renders), and the bench and hindsight totals with their own coverage counts (A11). So there is no new endpoint. Two quantities are missing and both belong on the server rather than in the client: per-lane **win rates**, which must live in `season_summary` because that is where the graded-counter honesty rule lives (A12), and **rank**, which does not exist anywhere in this tree and needs one additive key off a JSON row `my_decisions` already reads (A13).
- **W4 (Tasks 11-15)** closes: the route-pin restructure spec §0 orders — **behind a STOP** — then the rails, the README, the gate checklist and the ROADMAP.

**This cycle adds no route.** Not one. All three views are served by additive fields on payloads that already exist, which makes v11 the cheapest cycle in which to pay the route-pin toll: the restructure changes no assertion's *verdict*, only where the verdict lives (A15).

**Frontend work is the bulk of this cycle.** Six surfaces move — a new Planning tab, Planning's tab control itself, `ComparePanel`, a new Model tab, and the two hub-level tab strips — and every one of them lands under v9b's two standing conventions: nothing scrolls the body sideways at 390px, and no table sits outside its own `overflow-x-auto`. Plus a third, from spec §Gates: **every one of the three new views has an empty state that a cold clone reaches**, and the cold-clone rail only renders each hub's *default* tab, so those tests have to be written per view rather than assumed (A18).

## Ambiguities the spec left open, and how this plan settles them

Eighteen. Six of them are findings rather than decisions, and three of those six make a workstream smaller than the spec budgeted for.

### A1 — §F2 is already half-shipped, and the plan's first job is to say which half.

The spec describes `ComparePanel` as if it renders a price, an xPts and a sparkline. Read it (`frontend/src/hubs/players/ComparePanel.tsx`, 214 lines) and it already does four of the things §F2 asks for:

| §F2 asks for | Already there? | Where |
| --- | --- | --- |
| EP component breakdown | **Yes**, as a grouped bar chart | fetch `L55-56`, pivot `L85-100`, chart `L104-119` |
| `p_play` / `p60` / xmins line | No — but the data is fetched | `ComponentFixture.minutes` is on the payload at `L56` and nothing reads it |
| set-piece and pen-taker flags | **Yes on the wire**, no on the page | `PlayerRow.penalties_order / free_kicks_order / corners_order` (`players.py:177-180`), passed in as `players` prop |
| next-6 ticker with difficulty chips | **Yes**, as `Badge`s with a three-way threshold | fetch `L58-59`, render `L184-206` |
| global / league EO / field EO | **Yes, all three** | `L159-178` — `league_eo`, `field_eo` + `field_class`, `ownership` |
| field EO **±SE** | **No, and it is the one real gap** | see A2 |

So W2 is not "build a comparison panel". It is: re-pivot a chart that already exists (A3), render three numbers already in the props (the set-piece flags), render a line already in a fetched payload (A5), restyle chips that already have the right data (A4), and add **one field** to one schema (A2). Writing it down this way matters, because a plan that budgeted §F2 as a new panel would have produced a second panel beside the first.

### A2 — the only server-side gap in §F2 is the standard error, and it is an additive field, not an endpoint.

`routers/players.py:149` calls `latest_field_eo()`, which returns `{element: {"eo", "se", "n", "gw"}}` (`data/field.py:202-250`). `:170` takes `.get("eo")` out of that dict and **drops `se` and `n` on the floor**. `PlayerRow` declares neither (`schemas.py:405-414`).

The ±SE therefore exists, in memory, in the router that serves the row, and stops one line short of the wire. v10b faced the same fact and reached the opposite conclusion — `field_frame.py` was built partly *because* `/api/players` carries no `se` (v10b plan A2) — and the difference is the consumer: v10b needed one number for one captain and would have paid ~700 rows of column for it; §F2 needs it **per compared player**, which is the row the explorer already sends.

**Settled: `PlayerRow` gains `field_se: float | None` and `field_n: int | None`, both defaulted, both filled from the dict already looked up.** No new endpoint, no route move, no second field-EO read. Both follow `field_eo`'s standing contract verbatim (`schemas.py:406-412`): **`None` means unknown and never 0.0**, because a standard error of zero is a claim of perfect precision from a 300-entry sample.

The residual v10b recorded — that `players.py:149` calls `latest_field_eo()` **unseasoned**, where `field_frame._field_table` passes `load_config().current_season` — is **deliberately not fixed here.** It is one keyword, and it is tempting because Task 2 opens the very line above it. It stays open for two reasons: the log holds one season today so the change is invisible until August 2027, and `tests/test_v8c_degradation.py` is protected and pins this exact call's behaviour over fixtures that carry no `season` column, where a season filter returns `{}` rather than today's answer. Closing it means moving a protected pin for a bug that cannot fire for eleven months. It is re-recorded in Task 13's README line.

### A3 — the stacked signed breakdown is a re-pivot, and the payload's zero-dropping is kept.

`components.py:147-150` builds `Component{label, points}` per fixture **dropping every term that rounds to 0.00**, and its module docstring says why: *"a panel whose job is showing what moved should not print nine zeroes to get to the one number that did."* `ComparePanel:85-100` then pivots that to one chart row per *label* with one bar series per *player* — which answers "who gets more from goals" and not "where does his EP come from".

§F2 asks for the transpose: one breakdown per player, stacked, signed.

**Settled: the existing grouped chart stays and a per-player signed breakdown is added inside each player's card.** Not a second recharts chart — a list of `(label, points)` rows with a bar whose direction encodes the sign, in the shape `kit/ThresholdBar` already establishes for a signed quantity. Three reasons, and the third is the one that decides it:

1. A stacked recharts bar with eleven series needs eleven distinguishable colours; `SERIES_COLOURS` has four and inventing seven more is a palette decision this cycle has no business making.
2. Negative segments in a recharts stack render below the axis and stop reading as parts of a whole, which is the entire point of a stacked breakdown.
3. The card is `md:grid-cols-2 lg:grid-cols-4` (`L124`), so at 390px each breakdown is a full-width column — where rows read and an eleven-series stack does not.

**Zeros stay dropped**, which is the payload's own honesty rule and not this cycle's to overturn. The breakdown's contract is that its rows sum to the xPts printed above them, and that holds whether or not a zero row is drawn. Include the sum as a visible total line so the claim is checkable on the page rather than asserted in a docstring.

### A4 — the difficulty chips use `difficultyBackground` inline; `FixtureChip` is not lifted.

The spec says "the v9b Timeline pattern". That pattern is `Timeline.tsx:152-155`: an inline `style={{ background: difficultyBackground(cell.difficulty) }}` on a plain span, with `difficultyBackground` imported from `kit/scale.ts:10-18` (exported through `kit/index.ts:33`). `FixtureTicker.tsx:108-112` and `FixtureMatrix.tsx:84` are the same idiom.

`kit/PlayerCard.tsx:119-153` also has a `FixtureChip`, and it is **module-private and takes a different type**: the frontend `NextFixture` (`types.ts:8-13`) is `{opponent_short, home, kickoff_utc, difficulty}`, which is neither the backend `NextFixture` schema nor a `MatrixCell`.

**Settled: `ComparePanel` follows Timeline's idiom and `FixtureChip` is not exported.** Lifting a private pitch-card component into `kit/` and widening its prop type to accept a third fixture shape is a refactor of a shipped page in service of a chip.

One thing that must **not** be lost in the restyle: `ComparePanel:191-194` picks `cell.defence` for GKP/DEF and `cell.attack` otherwise, and its comment records why (*"Colouring every card by `attack` told a goalkeeper's owner about his chances of scoring"*). `MatrixCell` carries no single `difficulty`; the position-correct score is chosen on the client and that choice survives the change. The chips gain the `difficultyBackground` tint and the home/away + gameweek title they already have; they lose the three-way `Badge` variant, which was a coarser reading of the same number.

### A5 — the minutes line is per fixture, and a double gameweek shows both rather than an average.

`ComponentFixture.minutes` is `MinutesOutput{p_play, p60, xmins}` (`schemas.py:456-467`), computed at `components.py:159-169`, and `_xmins` returns `None` — never 0.0 — when either probability is missing, for the reason its docstring gives: *"a different and much stronger claim."*

The panel has `components` in state and never reads `minutes`. The question the spec leaves open is what to print when a player has two fixtures in the gameweek.

**Settled: the line names the requested gameweek's fixtures, and a double gameweek prints both, side by side, labelled by opponent.** Not a mean (`p_play` averaged over two fixtures is a probability of nothing) and not a sum (`p60` does not add). xMins is the one of the three that *does* add across fixtures, so a total is shown beside the pair. A fixture whose `p_play` is `None` prints an em dash and never a zero — the `fmtNum` convention the panel already uses.

### A6 — the "try changes" handoff is not a deep link, because this app has none, and it costs Planning's tabs their `defaultValue`.

The spec calls it a deep-link and names ChipsTab's "Try it" as the pattern. Both need correcting before anyone implements a URL scheme that does not exist:

- `App.tsx:16` registers `/planning` and nothing else. No component in the app reads `useSearchParams` or a hash. There is no route state to link into.
- `ChipsTab.tsx:125-129`'s "Try it" is a **local prefill**: it sets ChipsTab's own `request` state and renders its own `ConstraintsPanel` + Re-solve button in a card on the same tab. It never navigates.
- The genuine cross-tab handoff already in the tree is different again: `Planning.tsx:34` hoists `whatif: WhatIfRequest` above the tabs, passes it as `value`/`onChange` into `WhatIfTab` (`:90`) and as `current` into `DraftsTab` (`:92`). The hoisting exists because Radix unmounts inactive tabs — the comment at `Planning.tsx:18-20` says so.

**Settled: the board's "Try these changes" writes the hoisted `whatif` state and switches the tab.** Which means `Tabs.Root` at `Planning.tsx:77` stops being uncontrolled: `defaultValue="timeline"` becomes `value={tab} onValueChange={setTab}` over a `useState('timeline')`. That is a real change to a shipped control and it gets its own test — the existing five tabs must still switch by click after the change, because a controlled Radix root that forgets `onValueChange` renders a tab strip nothing can move.

This is **not** a view preference and is not persisted, for the reason `ThisWeek.tsx:31-34` already gives about the pitch/table toggle: *"persisting a view preference is a real feature with real questions behind it … and inventing an answer inside a lean UI cycle is how a preference store gets built by accident."*

### A7 — the constraint vocabulary cannot say "sell exactly this", and the button says so rather than pretending.

`ConstraintsPanel.tsx` offers exactly `lock` / `ban` / `force_in` (player lists), `max_hits` (0-3), `chip` (`none|wc|bb|fh|tc`), `horizon` (null or 1-6). `WhatIfRequest` (`schemas.py:64-70`) has no `must_buy`, no `must_sell`, no bank.

So the board's week, which names buys and sells, maps onto that vocabulary imperfectly:

- planned **buys** → `force_in` (the solve must include them) — an exact fit;
- planned **sells** → `ban` (the solve may not hold them) — **not** an exact fit: `ban` forbids buying him back as well, which is a stronger constraint than "sell him";
- the week's **chip** → `chip` via `ChipsTab.tsx:25-30`'s `CHIP_CODES` map, imported rather than re-declared;
- **hits** → `max_hits`, clamped to the panel's 0-3 range;
- **bank** → nothing. There is no constraint for it.

**Settled: the mapping is made and the imprecision is printed under the button**, in the voice `Timeline.tsx:35-36` uses about its own degradations: one sentence saying that a sell is carried across as "don't own him", which also rules out buying him back, and that the bank is not a constraint the lab accepts. The alternative — inventing `must_sell` — is a change to `whatif.py`, which is protected, and to the solver's constraint set, which is the thing spec §Non-goals forbids.

### A8 — the bank trajectory does not exist, is derived at the router, and goes `None` from the first unpriced move onward.

`advise.py:966-970` writes each `plan_by_gw` entry with exactly `gw, hits, buys, sells, expected_pts`. There is no money in it. `PlanGw` (`schemas.py:997-1006`) mirrors that plus `hit_cost`, `chip`, `captain`, `vice`. Nothing anywhere serves a bank.

The bank *is* on disk: `SolveState.bank`, in tenths of a million (`artifacts.py:154`), written at `advise.py:1003`, and **`plan.py:130` already loads the solve state** — for the price columns it already joins.

**Settled — all in `schemas.py` and `routers/plan.py`, both unprotected.** `PlanTimeline` gains `bank: float | None` (the starting bank, in millions, via the existing `_price` helper which is exactly the tenths→millions conversion). `PlanGw` gains `bank: float | None`, the bank *after* that week's moves, running forward:

```
bank[0] = state.bank / 10
bank[t] = bank[t-1] + Σ sells[t].price − Σ buys[t].price
```

**And the rule that makes it honest: a week containing a move whose `price` is `None` has `bank = None`, and so does every week after it.** `_prices` already leaves a side unpriced when the pool lacks the column or the cell is not a number (`plan.py:50-71`), and a running total that silently skipped such a move would report a *confident* bank that is wrong by exactly that player's price — which is worse than no bank, because the reader cannot see the gap. Once the trajectory is broken it stays broken; there is no re-synchronisation point.

This is arithmetic the solver already did internally and the router is re-doing. That is a real duplication and it is accepted rather than hidden: the alternative is widening `plan_by_gw`, which is `advise.py`. It is recorded as a residual in Task 13.

### A9 — `/api/prices/movers` is a finished endpoint with no consumer, and it is §F1's price warning.

`routers/prices.py` serves `GET /api/prices/movers → MoversPanel`, and the frontend fetches it from **nowhere**: `MoversPanel`/`MoverRow` are declared in `types.ts:1249-1266` with zero consumers outside tests. It reads `digest.freshest_prices()` and `watchlist.watch_targets()` (squad + plan + watchlist) and never touches the network.

`MoverRow` (`schemas.py:1499-1517`) is `code, name, now_cost, price_change_percent, direction ("rise"|"drop", never flat), calibrating, source ("squad"|"plan"|"watchlist")`. Note what it is **not**: there is no predicted new price and no delta. It is percent-of-threshold and a direction, and `prices.py:9-16` alerts at |pct| ≥ 90.

**Settled: the board fetches `/api/prices/movers` and joins by `code` onto each week's buys and sells.** Zero backend diff for this half. The warning renders as the direction plus the percentage, never as a predicted price, because the payload does not contain one and a board that printed "→ £8.6m" would be inventing the number. `calibrating: true` suppresses the warning entirely — the field exists to say the log is not yet trustworthy, and a warning drawn from an untrustworthy log is worse than none.

The fetch fails soft, like Timeline's ticker fetch (`Timeline.tsx:60, 145`): no warnings drawn, board unchanged, no error surface. A price decoration must never be the reason a plan does not render.

### A10 — the board re-fetches `/api/plan/{gw}` rather than sharing Timeline's.

`PlanTimeline` has exactly one reader in the tree (`Timeline.tsx:40`), and Radix unmounts inactive tabs, so a board on a sixth tab would fetch it again on first open.

**Settled: it fetches its own, and the hoisting `Planning.tsx` already does is not extended to the plan.** The state hoisted above the tabs today is state that is *shared* (`whatif` is edited on one tab and saved on another) or *expensive to re-derive* (`teamByCode`). A read-only GET of a JSON file on localhost is neither. Hoisting it would put a second fetch in the hub for the benefit of a tab the reader may never open, and would couple Timeline's lifetime to the board's.

The two views therefore read the same endpoint and must not disagree about it: the board reads `week.buys/sells/hits/hit_cost/chip/expected_pts` with the same accessors Timeline uses (`Timeline.tsx:97-126`), plus the new `bank`.

### A11 — §F3's decision-quality half is already on the wire, and there is no new endpoint.

`routers/review.py` is 34 lines and serves `GET /api/review → Review(gws=ledger, summary=season_summary(ledger))`. So `season_summary`'s entire return is already a client-side object:

```
{"gws", "lanes": {lane: {"pts","pwin","graded"}}, "accuracy": [{"gw","accuracy"}],
 "points_on_bench", "points_on_bench_gws", "hindsight_gap", "hindsight_gap_gws",
 "reconciled_gws", "unreconciled_gws", "best", "worst"}
```

Against the dashboard's needs: the lanes with graded counters — served. Cumulative points-on-bench with its coverage count — served (`points_on_bench` / `points_on_bench_gws`), and per-GW on `gws[].points_on_bench` for the trajectory. Hindsight gap and its count — served. **The per-GW accuracy series is served and is currently rendered by nothing** (`ReviewTab.tsx` reads the lanes, the bench sentence and the worst decision, and never touches `summary.accuracy`). Calibration is a separate route that already exists and already carries a per-GW-per-head Brier (`CalibrationReport.gameweeks[].heads[k].brier`, `schemas.py:958-985`).

**Settled: no new endpoint, and `GET /api/review`'s never-errors contract (`routers/review.py:32-34`) is not touched.** Two additive fields go onto what it already serves (A12, A13), which is the spec's own instruction — *"prefer serving derived numbers next to the ledger the way season_summary already does — reuse it, never re-derive."*

### A12 — per-lane win rates are not served, and they belong in `season_summary` rather than in the client.

Every `ReviewLane` carries a `label` (`Brilliant|Good|Aligned|Inaccuracy|Blunder|None`) and a `delta_pts`, and every one of them is on the wire in `gws[]`. So a client *could* count them.

It must not, and the reason is the rule the spec names: `season_summary`'s docstring (`review.py:1109-1115`) is where "an ungraded lane contributes nothing to the sum *and* nothing to the count" is written down, and `schemas.py:1248-1249` restates it — *"`pts` of zero over `graded` of zero is 'never measured', not 'never wrong'."* A win rate computed in a React component would be a second implementation of that rule, in a language with a different notion of null, drawn on the same page as the first.

**Settled: `ReviewLaneTotal` gains `wins: int` and `losses: int`, counted inside `season_summary` in the same loop, under the same `delta_pts is None → skip` guard the totals already use.** A win is `delta_pts > 0`, a loss is `delta_pts < 0`, and **a zero delta is neither** — it is a week the decision made no difference, and folding it into either side would let a lane of perfect agreement read as a lane of perfect judgment. `wins + losses <= graded` therefore holds with slack, and the rail asserts the inequality rather than an equality. The client renders `wins/graded` and, when `graded == 0`, renders the same "never graded" text `ReviewTab.tsx` already uses.

### A13 — rank does not exist anywhere in this tree, and the field it needs will be null for every already-banked row, forever.

The spec's first §F3 bullet asks for "rank trajectory vs decision quality over the graded `ReviewGw` rows" and then cites the fields — lanes, points_on_bench, accuracy, hindsight.
