## Ambiguities the spec left open, and how this plan settles them

Fourteen things §1-§4 do not pin, including two places where the tree is kinder than the spec expected, one where it is harsher, and one where the spec describes a quantity it does not have. Each is decided once here so no task decides it twice at the keyboard.

### A1 — the own-side Understat switch has an exact precedent in the same file, and it includes the `latest` fill.

`add_context` (`engineer.py:664-690`) is v9c's own switched Elo merge and it is the shape Task 1 copies verbatim:

```python
df = df.copy()
df["_club"] = as_of_club(df)
team_elo = elo.rename(columns={"code": "_club", "elo_pre": "team_elo"})
df = df.merge(team_elo, on=["season_idx", "gw", "_club"], how="left",
              validate="many_to_one")
...
df["team_elo"] = df["team_elo"].fillna(df["_club"].map(elo_final))
...
df = df.drop(columns=["_club"])
```

Two things follow, and the second is the one the spec does not say out loud.

1. `_club` is a temporary column built with `as_of_club`, the merge renames the lookup frame's club column to `_club`, and `_club` is dropped at the end. `merge_understat_team` already drops `_date` on its last line (`:999`); `_club` joins it there.
2. **The `latest` fallback fill switches too.** `merge_understat_team:995` reads `out["team_code"].map(latest[col])`, and `add_context:687` is the identical construct one screen up — v9c switched *that* one to `_club`. Leaving the Understat fill on `team_code` would put the two halves of one merge on two different club keys, which is precisely the split-brain the finding is about. The **opponent** side of both the merge (`:983-985`) and the fill (`:997-998`) stays on `opp_code`, untouched, for the reason `bps.py:79-80` gives: `opp_code` is written per row from the fixture at ingest and already survives a transfer.

### A2 — the `latest` fill is where the switch is least likely to matter, and saying so is part of the measurement.

`latest_understat_team` is indexed by *current* `team_code` and exists to fill rows the date join could not match — overwhelmingly future fixtures, where `as_of_club` returns `team_code` by construction (A6 of the v9c plan). So the fill's switch changes an answer only for a **historical** row that missed the date join *and* belongs to a transferred player. That population may well be empty. G1 reports it as its own number rather than folding it into the merge's divergence, so "the fill changed nothing" is recorded as a result instead of being assumed.

### A3 — the congestion switch keeps its guard, and the guard is about a *column*, not a value.

`_recent_load:544` reads `if cups is None or cups.empty or "team_code" not in df.columns: return own`. That check stays exactly as written even though line 553 stops reading `df["team_code"]` directly, because `as_of_club` **falls back to `df["team_code"]`** and raises `KeyError` without it. Removing the guard as "now unused" would turn a clean early return into a crash on the simple-component frames that carry no club at all. The switch is one line:

```python
clubs = pd.to_numeric(as_of_club(df), errors="coerce")
```

### A4 — `engineer.py:453-460` is not touched, and the file says why.

The rotation-probe frame at `:444-460` builds its own tail and comments that `team_code` and `as_of_club` are equivalent there. The comment is a standing instruction. Task 2 does not touch it and Task 10 pins that it did not.

### A5 — G1 is a divergence measurement, not an arm, so it has no keep rule and it does not run `evaluate_benchmark`.

Spec §1 asks for two numbers per consumer — the share of rows where the switch *changes the consumer's inputs*, and a match-rate sanity check — and nothing else. There is no eval delta to gate on and none is pre-registered, because spec §1 is v9c's D2 continued and D2's contract was explicit: the fix ships either way, since a regression would mean the old number was flattered by leakage. `scripts/v9d_club_eval.py` is therefore **much cheaper than `v9c_club_eval.py`**: one `load_training_frame()` and two builder re-runs, no benchmark refits.

The lever this time **is** connected, and for a reason worth stating: both switched sites look `as_of_club` up as a module global at call time, so `engineer.as_of_club = _stamped` genuinely changes what they read. v9c's `ROLL_STATS` was the opposite — bound as a mutable default argument on four functions, so rebinding the module global did nothing and both arms silently built the same frame. The difference is real, and it is exactly why the guard below stays anyway.

It keeps v9c's **lever guard**, which is this project's twice-learned lesson (v9c run-2's zeros): before reporting anything it asserts that `as_of_club(df) != df["team_code"]` on a non-zero number of rows. If the frame carries no `club_code`, both arms are the same arm and every number below is a decorated zero — the script exits rather than printing one.

### A6 — the SSE rail is a source inspection, because the thing being defended is a call shape.

Spec §2 wants a rail that catches "no import-string + `workers=` drift can land silently". There is nothing to execute: `cli.ui` calls `uvicorn.run(create_app(), ...)` and starting a real server in a test would be a different test. So the rail reads `inspect.getsource(gaffer.cli)`, finds the `uvicorn.run(` call, and asserts (a) its first argument is `create_app()` and not a quoted module path, and (b) the word `workers` does not appear in the call. This is the same idiom `tests/test_v9c_degradation.py:337` already uses for the protected `advise.py` write.

### A7 — identity's memo covers the three parquet readers and deliberately **not** `_difficulty_by_team`.

Spec §3a says "and whatever `_difficulty_by_team` reads". What it reads is `meta.ticker(weeks=2)` — sixty lines composing odds, Elo and the fixture list, with its own failure semantics and its own idea of which gameweeks are in the window. There is no single backing file to stat, so a `(path, mtime_ns, size)` key cannot express its identity, and a key that pretends to would serve a stale difficulty tint after an odds refresh. It stays uncached, and the residual is recorded.

The consequence for the rail: the spec's "a second `with_identity` call does **zero** `store.load` calls" cannot hold literally, because the ticker loads on every call. The rail therefore spies on `store.load` and asserts that **none of the three identity paths** — `live/teams.parquet`, `live/players.parquet`, `live/fixtures_all.parquet` — is re-read. Loads made by the ticker are allowed and named in the test's docstring so the next reader does not "tighten" the assertion into a false failure.

### A8 — the memo keys on the path resolved at call time, or it poisons the test suite.

`store.DATA_DIR` is a module-level `Path("data")` and the suite monkeypatches the process CWD (`monkeypatch.chdir(tmp_path)`) constantly. A cache keyed on the *relative* string alone would hand one test's `teams.parquet` to the next test's tmpdir. The key is therefore `(str(store.DATA_DIR / rel), st_mtime_ns, st_size)`, resolved on every call, and `_fixture_by_team`'s key additionally carries the gameweek and the teams file's key, because its output embeds short names read from `teams.parquet`.

One slot per relative path, so the cache holds at most three entries and a changed file evicts its own.

A `stat` failure is not an error path: it means "read the file uncached", exactly as the module's standing contract ("nothing here raises") requires.

### A9 — §3c is expressible: the holder's kind **is** knowable at `jobs.py:321`.

The spec offers an out — "if the running job's kind is not knowable at that point without restructuring, keep the constant and record it". It is knowable. `start` takes `self._lock` at `:315` and `self._current` is read at `:322`; `self._runs[self._current].kind` is a plain attribute on the `JobRun` dataclass (`jobs.py:151`). No restructuring is needed.

What it costs is that the spec's one-line replacement becomes **three lines**, because `self._current` may be `None` and the spec's suggested expression references a `run` that does not exist yet at that point (`run` is constructed four lines later). Task 6's STOP writes the three lines out verbatim and asks for them explicitly rather than smuggling a widened group in under "the `ADVISE_TIMEOUT_S` read".

### A10 — §3b changes no existing assertion, and that is checked rather than hoped.

The cancel path is `abandon_current()` → `_abandon_current(0.0)`; the timeout path is `start` → `_abandon_current(ABANDON_TIMEOUT_S[...])` with a positive number. Grepped, the assertions on that error string are:

### A11 — the calibration report grades **banked** predictions, and it never refits.

Spec §4 leaves the source to the planner: "the banked advice artifacts / snapshot path if available for that GW, else refit strictly-before … whichever the planner finds already exists". It exists, and it is neither of the two the spec guesses:

**`reports/components_gw{N}.parquet`**, written by `gaffer.artifacts.save_components` from `advise.py:944` on the weekly run — *before* the gameweek is played. `COMPONENT_COLS` (`artifacts.py:36-50`) carries `p_play`, `p60`, `p_cs`, `p_cs_model`, `e_goals` and `e_assists` per player. `load_components(gw)` (`artifacts.py:137`) reads it back.

That settles four things at once:

- **`p_play`, `p60`, `p_cs` come off the artifact directly.** These are the numbers the optimizer actually multiplied by that week, which is the only version of "calibrated" anybody cares about.
- **`p_haul` is recomputed, not stored** — `assemble.p_haul(e_goals, e_assists)` (`assemble.py:39`) from the banked components. That is the same function `assemble_ep:112` called at solve time, so the number is reproduced rather than approximated, and it is the attacking-haul quantity spec §4 names (`p_attacking_haul` at the web boundary since v9c).
- **`p_start` is omitted, with the reason in the payload.** It is not in `COMPONENT_COLS` — `predict_modes`' trichotomy is never banked. Spec §4 anticipates an omitted head and asks that the payload say so; this is the head, and the reason is "not banked", not "no starts column". The *outcome* side is checked too: if `player_gw.parquet` has no `starts` column the payload says that instead.
- **Nothing refits, so the report costs seconds.** A walk-forward refit would be ~38 `train_all` calls at the end of a season, and — worse — it would grade a *different* model from the one that served. `evaluate_current` already exists for the refit protocol; duplicating it here would put two protocols on one Brier trend and make the slope partly an artefact of which protocol each week used.

### A12 — a re-run of `advise` on a finished gameweek would overwrite the artifact with a post-hoc prediction, so the report refuses to grade it.

This is the one real hazard in A11 and the spec's "never grade a prediction made after the outcome" names it exactly. `save_components(frame, gw)` writes `gw{N}` whatever today's date is; pointing `advise` at a completed gameweek silently replaces an as-of prediction with a hindsight one, and nothing in the artifact records when it was written.

The guard uses the only signal there is — the file's mtime — against the only clock that matters, the gameweek's last kickoff from `live/fixtures_all.parquet`:

```
post_hoc  iff  components_gw{N}.parquet mtime  >  max(kickoff_time for gw N)
```

A gameweek flagged `post_hoc` is **excluded from both the per-GW rows and the cumulative pool**, and listed in the payload's `excluded` array with its reason, so a reader sees a gap and its cause rather than a suspiciously good Brier. mtime is a weak signal — a file copy moves it — so the guard is deliberately conservative in the direction of refusing to grade: a false exclusion loses a row, a false inclusion invents a result. Missing fixtures leave the check unable to run, which is also an exclusion (`reason: "kickoff unknown"`).

### A13 — `p60` is graded unconditionally, because that is what the banked number is.

Spec §4 writes the outcome as "`p60` (minutes ≥ 60 **given played**)". The parenthetical does not match the quantity. `MinutesModel.predict` (`models/minutes.py:260`) computes `p60 = p_start * P(60+ | start)` — an *unconditional* probability that this player reaches an hour, which is exactly how the assemble path uses it and exactly how `evaluate_current:346` already scores it (`(hold["minutes"] >= STARTER_MINUTES)`, over every held-out row).

Grading it "given played" would filter the outcome rows to `minutes > 0` while leaving the prediction unconditional, and the head would look badly under-confident for a reason that is entirely the scorer's. So the outcome is `minutes >= 60` over every row with a banked prediction, `STARTER_MINUTES` is read from `evaluation.py:244` rather than written as a literal, and this paragraph is quoted into `evaluate_calibration`'s docstring so the next reader finds the discrepancy already resolved instead of "fixing" it.

The three other outcomes are unambiguous and match the spec exactly: `p_play` is `minutes > 0`, `p_cs` is the team's clean sheet at team-gameweek grain, `p_haul` is `goals + assists >= 2`.

### A14 — the report is CLI-only, and that is a determination rather than a preference.

Spec §4's last bullet says "wire `--calibration` into the existing `evaluate` job kind's runner **if the job plumbing passes flags**". It does not, and cannot without a new kind:

- `JOB_KINDS` is `dict[str, Callable[[], Any]]` (`job_kinds.py:192`) — every value is **zero-argument**.
- `POST /api/jobs/{kind}` (`routers/jobs.py:31`) takes the kind from the path and no body at all.
- The precedent for a second evaluate mode is `news-shadow`, which is a *separate job kind* wrapping `evaluate_news_shadow` — and spec §0 pins `JOB_KINDS` at twelve.

So there is no wiring to do, the spec's own fallback applies ("CLI-only is acceptable for v9d and the UI card says how to run it"), and Task 9's empty state carries the command. Task 10 pins the twelve with this reasoning in its docstring, so the next cycle that wants a button knows it is buying a thirteenth kind and a moved pin, not a flag.

- [ ] **Write the failing test.** Create `tests/test_v9d_understat_club.py`:

```python
v9c derived ``club_code`` and switched three consumers onto it — the
position-by-club prior, manager-spell scoping, and the own side of the Elo
merge. ``bps.as_of_club_code``'s docstring names the two it deliberately left

is written per row from the fixture at ingest (``data/live.py:106``) and
already survives a transfer — ``bps.py:79-80`` says so — so switching it would
be a change with no finding behind it and a second thing to explain in the
replay delta.
"""

from __future__ import annotations

import pandas as pd

from gaffer.features.engineer import (TEAM_US_FEATURES,
                                      add_understat_team_rolling,
                                      merge_understat_team)


def _rolled() -> pd.DataFrame:
    """Two clubs with unmistakably different form on the same date."""
    return pd.DataFrame({
        "team_code": [1, 1, 3, 3],
        "date": ["2024-08-10", "2024-08-17", "2024-08-10", "2024-08-17"],
        "us_xga": [0.5, 0.5, 3.0, 3.0],
        "ppda": [8.0, 8.0, 20.0, 20.0],
    })


def _players() -> pd.DataFrame:
    """One player, stamped Arsenal (3) today, who played GW1 for Man Utd (1).

    ``club_code`` is what ``models.train.load_training_frame`` derives and
    what ``engineer.as_of_club`` reads; ``team_code`` is what the store
    stamped on him this morning.
    """
    return pd.DataFrame({
        "code": [7, 7],
        "season_idx": [3, 3],
        "gw": [1, 2],
        "kickoff_time": ["2024-08-17T14:00:00Z", "2024-08-24T14:00:00Z"],
        "team_code": [3, 3],
        "club_code": [1, 3],
        "opp_code": [43, 43],
    })


def test_the_own_side_reads_the_club_he_was_actually_at():
    """The finding, in one assertion. Before v9d his GW1 row carried
    Arsenal's xGA because Arsenal is where he plays *now*."""
    out = merge_understat_team(_players(), add_understat_team_rolling(_rolled()))
    # GW1: Man Utd's numbers, not Arsenal's.
    assert out["team_us_xga_r5"].iloc[0] == 0.5


def test_a_player_who_never_moved_is_unaffected():
```

```python
"""Gate G1, §1: what did closing the last two club-leak consumers change?

Not a gate and no keep rule. Spec §1 continues v9c's D2, whose contract was
explicit: the as-of club ships whether or not eval moves, because a regression
would mean the old number was flattered by leakage. So this script reports and
does not decide — and, unlike ``scripts/v9c_club_eval.py``, it runs no
benchmark at all. Spec §1 asks for two numbers per consumer and nothing else,
which makes this minutes rather than the hour v9c's cost:

* ``V9D_CLUB_UNDERSTAT`` — over the whole training frame: how many rows have
  ``as_of_club != team_code`` at all (the population that *can* change), how
  many of those actually see a different own-side Understat value once the
  merge runs both ways, and the own-side **match rate** (non-NaN own-side
  rows) on each side. The match rate is the sanity check spec §1 names: the
  switched join may not resolve fewer rows than the unswitched one.
* ``V9D_CLUB_CONGESTION`` — the same shape for ``matches_last_14d``: the
  diverging population, the rows whose count actually moves, and the mean
  absolute change on those rows.
* ``V9D_CLUB_DONE`` — both blocks together, banked to
  ``reports/v9d_club_eval.json``.

Run it, watch it, read the lines::

    mkdir -p logs && caffeinate -i nohup .venv/bin/python scripts/v9d_club_eval.py \\
        > logs/v9d_club_eval.log 2>&1 &
    grep -e V9D_CLUB_UNDERSTAT -e V9D_CLUB_CONGESTION -e V9D_CLUB_DONE \\
        logs/v9d_club_eval.log

**The lever guard.** Both arms are produced by monkeypatching
``engineer.as_of_club`` to return the stamped ``team_code`` — the smallest
possible intervention, running the identical code path on both sides. Before
anything is reported, ``main`` asserts that the real ``as_of_club`` differs
from ``team_code`` on a non-zero number of rows. If the training frame carries
no ``club_code`` the two arms are the same arm and every number below is a
decorated zero, which reads exactly like a clean negative result. v9c learned
this twice (its run-2 zeros); the script exits rather than printing one.
"""

from __future__ import annotations

import json
from pathlib import Path

import numpy as np
import pandas as pd

from gaffer.features import engineer

_REAL = engineer.as_of_club


def _stamped(df: pd.DataFrame) -> pd.Series:
    """The pre-v9d answer: whatever the store stamped on the row today."""
    return df["team_code"]


def _frame() -> tuple[pd.DataFrame, pd.DataFrame | None, pd.DataFrame | None]:
    """The training frame plus the two side inputs the switches read."""
    from gaffer.data import store
    from gaffer.models.train import load_training_frame

    df, _tg, _ = load_training_frame()
    rolled = (engineer.add_understat_team_rolling(store.load("history/understat_team.parquet"))
              if store.exists("history/understat_team.parquet") else None)
    cups = (store.load("history/cups.parquet")
            if store.exists("history/cups.parquet") else None)
    return df, rolled, cups


def _own_cols(frame: pd.DataFrame) -> list[str]:
    return [c for c in frame.columns
            if c.startswith("team_") and c.endswith(tuple(
                f"_r{w}" for w in engineer.TEAM_US_WINDOWS))]


def _differs(left: pd.Series, right: pd.Series) -> pd.Series:
    """Elementwise inequality that counts NaN-vs-value as a difference and
    NaN-vs-NaN as a match. ``!=`` alone calls two NaNs different, which would
    report every unmatched row as a change."""
    both_nan = left.isna() & right.isna()
    return (~both_nan) & (left.ne(right) | (left.isna() ^ right.isna()))


def understat_block(df: pd.DataFrame, rolled: pd.DataFrame | None) -> dict:
    on = engineer.merge_understat_team(df, rolled)
    engineer.as_of_club = _stamped
    try:
        off = engineer.merge_understat_team(df, rolled)
    finally:
        engineer.as_of_club = _REAL
    cols = _own_cols(on)
    changed = pd.Series(False, index=on.index)
    for col in cols:
        changed |= _differs(on[col], off[col])
    return {
        "rows": int(len(df)),
        "own_columns": len(cols),
        "changed_rows": int(changed.sum()),
        "changed_share": round(float(changed.mean()), 6),
        "match_rate_on": round(float(on[cols[0]].notna().mean()), 6),
        "match_rate_off": round(float(off[cols[0]].notna().mean()), 6),
    }


def congestion_block(df: pd.DataFrame, cups: pd.DataFrame | None) -> dict:
    col = "matches_last_14d"
    on = engineer.add_congestion(df, cups)[col]
    engineer.as_of_club = _stamped
    try:
        off = engineer.add_congestion(df, cups)[col]
    finally:
        engineer.as_of_club = _REAL
    changed = _differs(on, off)
    delta = (on - off).abs()
    return {
        "rows": int(len(df)),
        "changed_rows": int(changed.sum()),
        "changed_share": round(float(changed.mean()), 6),
        "mean_abs_change_on_changed_rows": (
            round(float(delta[changed].mean()), 4) if changed.any() else 0.0),
        "mean_on": round(float(np.nanmean(on)), 4),
        "mean_off": round(float(np.nanmean(off)), 4),
    }


def main() -> None:
    df, rolled, cups = _frame()

    diverging = int((_REAL(df) != df["team_code"]).sum())
    if diverging == 0:
        raise SystemExit(
            "the lever is disconnected: as_of_club equals team_code on every "
            "row of the training frame, so both arms below would be the same "
            "arm and every number a decorated zero. Check that "
            "load_training_frame still derives club_code (v9c A7).")

    out = {
        "diverging_rows": diverging,
        "diverging_share": round(diverging / max(len(df), 1), 6),
        "understat": understat_block(df, rolled),
        "congestion": congestion_block(df, cups),
    }
    print("V9D_CLUB_UNDERSTAT", json.dumps(out["understat"]), flush=True)
    print("V9D_CLUB_CONGESTION", json.dumps(out["congestion"]), flush=True)
    print("V9D_CLUB_DONE", json.dumps(out), flush=True)

    if out["understat"]["match_rate_on"] < out["understat"]["match_rate_off"]:
        # Reported, not silenced: spec §1's sanity check is that the switched
        # join resolves no fewer rows than the unswitched one.
        print("V9D_CLUB_MATCH_RATE_REGRESSED", flush=True)

    Path("reports").mkdir(exist_ok=True)
    Path("reports/v9d_club_eval.json").write_text(
        json.dumps(out, indent=1, default=str))


if __name__ == "__main__":
    main()
```

```python
def _file_key(rel: str) -> tuple | None:
    """``(path, mtime_ns, size)``, or ``None`` when the file cannot be stat'd.

    ``None`` means "read it uncached", not "fail": this module's standing
    contract is that nothing here raises, and a missing snapshot is already
    handled by every caller below.

        path = store.DATA_DIR / rel
        st = path.stat()
        return (str(path), st.st_mtime_ns, st.st_size)
    except OSError:
        return None


def _memo(slot: str, key: tuple | None, build: Callable[[], Any]) -> Any:
    """``build()``, memoised under ``slot`` while ``key`` holds."""
    if key is None:
        return build()
    hit = _CACHE.get(slot)
    if hit is not None and hit[0] == key:
        return hit[1]
    value = build()
    _CACHE[slot] = (key, value)
    return value

    """Drop every memoised map. For tests, and for a reader who wants one."""
    _CACHE.clear()
```

```python
"""Below this a head reports ``insufficient`` instead of a curve.

Ten reliability bins over twenty rows is a picture of the sampling noise, and
a trend line drawn through pictures of noise is worse than no trend line: it
is a number people act on. Thirty is the smallest count at which the bins say
anything at all, and the payload says which side of it each head fell.
"""


def calibration_head(pred, actual) -> dict:
    """One head's calibration, in a shape that is the same either way.

    ``status`` carries the "not enough data" case rather than a missing key,
    so nothing downstream — pydantic, the card, a later script — has to branch
    on whether ``brier`` exists.
    """
    p, y = _paired(pred, actual)
    n = int(p.size)
    if n < MIN_CALIBRATION_SAMPLES:
        return {"status": "insufficient", "n": n, "brier": None,
                "log_loss": None, "reliability": []}
    b, ll = brier(p, y), log_loss(p, y)
    return {"status": "scored", "n": n,
            "brier": None if np.isnan(b) else round(b, 4),
            "log_loss": None if np.isnan(ll) else round(ll, 4),
            "reliability": reliability(p, y)}
```

## Notes for the implementer

- **Task order is mostly free, with three constraints.** T1 and T2 must precede T3 (the instrument measures the switches). T4 creates `tests/test_v9d_degradation.py`, so it precedes T10. T7 → T8 → T9 is a strict chain: the schema mirrors the payload and the card mirrors the schema. Everything else can be done in any order.
- **Task 6 is the only STOP that gates code.** Tasks 3 and 11 stop before *running* something; Task 6 stops before *writing* something. Do not start its `jobs.py` half without the orchestrator's acknowledgement in-branch, and run the circular-import check first — where the `ABANDON_TIMEOUT_S` import lands is part of what is being authorized.
- **This plan takes spec §3c's harder branch and says why.** The spec allows keeping the single constant if the holder's kind is not knowable at `jobs.py:321`. It is knowable (A9). What that costs is three lines where the spec wrote one, in the same place, which is enumerated rather than smuggled.
- **This plan also declines one thing the spec implies.** §3a says to cache "whatever `_difficulty_by_team` reads". It reads `meta.ticker`, which has no single backing file, so it stays uncached and the rail counts reads of the three identity paths rather than all `store.load` calls (A7). A rail written the literal way would fail on the ticker's own reads and the next person would loosen it in the wrong direction.
- **The calibration report's value is entirely in its refusals.** The Brier numbers are easy; `omitted`, `excluded` and `missing` are what stop it being a plausible-looking grade of hindsight (A12). If a later cycle finds them noisy and drops them from the card, the card becomes actively misleading — worse than not existing.
- **The post-hoc guard leans on mtime, which is a weak signal, deliberately in the safe direction.** A copied file is falsely excluded and one row is lost; a re-run advise that slipped through would be graded against the outcome it already saw. If a stronger signal ever lands — a `written_at` column in `COMPONENT_COLS`, say — that is the moment to revisit, and it is a one-line change in one place.
- **Never stage `reports/` or `logs/`.** T3 and T11 both write there, and the numbers reach the repo only by being transcribed into the spec (CONVENTIONS §4). A banked JSON in a commit is a number nobody can re-read in six months.
- **`scripts/v9c_replay.sh` and `scripts/v9c_club_eval.py` are evidence, not utilities.** They produced v9c's banked verdicts. T11 copies rather than edits, and T12's audit checks that both are still byte-identical to `main`.
