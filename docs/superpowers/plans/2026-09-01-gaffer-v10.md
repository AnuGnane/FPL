## Ambiguities the spec left open, and how this plan settles them

Fifteen. One of them (A8) is a finding rather than a decision: the seam §F1 assumes exists does not, and the plan stops in front of it instead of walking around it.

### A1 — the two-pass, concretely: what pass two fixes, what it frees, and what happens when it fails.

Spec §F1a asks for an "acceptable answer" and this is it, spelled out so no task invents a second version.

**Pass one** is today's solve, byte-for-byte, with `p_play` used for nothing but bench *ordering* (§F1b, which needs no re-solve — it is post-processing on an already-chosen squad). It always runs and it is always the fallback.

**Between the passes**, per gameweek `t` of the horizon, three numbers come off pass one's answer:

```
out_frailty[t] = clamp( mean(1 - p_play[c][t] for c in xi[t]) / POPULATION_DNP )
gk_frailty[t]  = clamp( (1 - p_play[keeper[t]][t])          / POPULATION_DNP )
vice_scale[t]  = clamp( (1 - p_play[captain[t]][t])         / POPULATION_DNP )
```

The same denominator and the same clamp in all three, which is what makes the byte-identity contract of A2 hold for the whole of §F1 rather than for two thirds of it.

**Pass two** rebuilds the identical problem with the three outfield bench-slot weights multiplied by `out_frailty[t]`, the reserve keeper's weight by `gk_frailty[t]`, and the vice term by `vice_scale[t]` — and pins `xi[c][t]` to pass one's XI and `cap[c][t]` to pass one's captain. Free in pass two: the four non-XI squad members, the bench slot assignment, the vice, the transfers that reach the bench, the bank, the free transfers. That is spec §F1a's "XI fixed, free-choice bench".

**Why the captain is pinned too**, which the spec does not say: `vice_scale[t]` is *the captain's* frailty. Leaving `cap` free in pass two would let the solver re-elect a different captain under a weight computed from the old one — the objective would then be pricing a hedge against a player who is no longer wearing the armband. Pinning both is what makes the two-pass approximation self-consistent, and it costs nothing the cycle wants: §F1 changes no captaincy term, so pass two has no new reason to move the armband.

**On infeasibility, pass one's answer is returned**, with a printed line. Pass two is a refinement and never a gate. Three ways it can fail and all three take the same exit: `pulp` returning a non-`Optimal` status (which `_solve_once` already turns into `RuntimeError`), the solver process dying, and the pinned XI being unreachable under a `FixedMoves` the policy layer supplied. The `except` is broad and carries `# noqa: BLE001` with the reason, the same posture `advise.py` takes around news.

**Cost:** two MILP solves where there was one, on the raw optimum and on `policy.coherent_plan`. Scenario re-solves are **not** doubled — `run_scenarios` is handed `**solve_kw`, which is assembled in `advise.py` and cannot learn a new keyword (A8), so every scenario stays single-pass. Task 12's STOP records the wall-clock delta as part of G2.

### A2 — "byte-identical when p_play is absent **or uniform**" is one guard, not two, and it is the reason §F1 is safe.

The orchestrator's non-negotiable is that today's solve is reproduced exactly when `p_play` is absent or uniform. Reproducing it under *absence* is easy — default `None`, no second pass. Under *uniformity* it is not, and the naive reading of spec §F1a gets it wrong: with every player at `p_play = p`, `out_frailty` is `(1-p)/POPULATION_DNP`, a scalar that multiplies the whole bench block and shifts it against the XI block. The XI choice can move. That is not decision-identical, and spec §F1a explicitly asks that it be.

So the guard is a single short-circuit, applied once, in front of the whole of §F1:

> **A `p_play` with no spread carries no information, so §F1 does not run.**

`_p_play_lookup` returns `None` — and §F1a, §F1b and §F1c are all inert — when any of these holds:

1. `p_play` is `None` or empty (today's every caller).
2. Coverage is incomplete: any `(code, gw)` in the filtered pool × horizon is missing, or is not a finite number in `[0, 1]`. **All-or-nothing**, because a pool where half the players have a probability and half are silently treated as 1.0 would price the silent half as nailed on, which is the one direction that actively misleads.
3. `max - min < P_PLAY_MIN_SPREAD` (`1e-9`) across every value in that grid.

Rule 3 is what makes "uniform" literally byte-identical rather than approximately so, at any value of `p` — including `p = 0`, which would otherwise collapse §F1b's ordering key to a field of zeros and scramble the bench into pool order. Rule 2 is what makes a partially-wired caller fail *closed*.

Task 9's rails assert all three, and assert them at the level that cannot be faked: a spy on `milp._solve` that counts **one** call and captures the LP text, compared character-for-character against a call that passes no `p_play` at all.

### A3 — `POPULATION_DNP` is measured before it is written, and the task order says so.

Spec §F1a wants "a documented `POPULATION_DNP` derived from the same replay data that fitted the curve". A number invented at the keyboard would make the normalisation decorative: the whole point of dividing by it is that a *typical* XI reproduces `DEFAULT_BENCH_CURVE` exactly, and that is only true if the divisor really is the typical XI's did-not-play rate.

The replay that fitted the curve is not re-runnable cheaply, so Task 7 measures the same quantity on the same footing as every other model number in this repo — the 2024-25 walk-forward benchmark:

> For each gameweek of the benchmark test season, take the positionally-legal eleven with the highest EP (`XI_BOUNDS`, greedy by EP, GK first) out of that gameweek's `DEFAULT_TOP_N` pool. `POPULATION_DNP` is the mean of `1 - p_play` over those XI slots, averaged over gameweeks.

Top-eleven-by-EP is a proxy for "the XI a points-max solver picks", and it is a *good* proxy for exactly the reason it is cheap: the MILP's XI is chosen from a 70-man EP-ranked pool by EP, subject to constraints (budget, three-per-club) that are close to orthogonal to availability. The driver also prints the GK-only rate and the per-gameweek spread, so the next cycle can split the constant if the two diverge; v10 ships one number and says why in its docstring.

**Task 7 runs before Task 8** and Task 8 does not begin until the number exists. There is no placeholder in this plan, and there must be none in the tree.

### A4 — the clamp is load-bearing and needs its own justification.

`FRAILTY_CLAMP = (0.25, 2.0)`, applied to all three ratios in A1.

The floor defends against a nailed-on XI. Eleven players at `p_play = 0.98` give a frailty near zero, which prices the bench at near zero — and a bench worth nothing is a bench the solver fills with the cheapest legal bodies to free up money for the XI. That is a real strategy and it is *not* what §F1a is asking for: the curve's third weight is `0.002` precisely because the third sub is nearly worthless, and the first is `0.21` because the first is not. A floor of 0.25 keeps the shape of the curve alive while still saying "this XI barely needs cover".

The ceiling defends against the opposite. A doubt-riddled XI at frailty 4 would price the bench like a permanent bench boost and buy a £5.5m fifth midfielder over a £9m starter. 2.0 is "twice as fragile as the league" and is already an aggressive claim.

Both bounds are constants beside `POPULATION_DNP`, pinned in Task 13, and the driver in Task 7 prints the observed per-gameweek range so the orchestrator can see whether the clamp ever binds on real data.

### A5 — RotoWire is fetchable, and here is what one fetch found.

One request, browser UA, no retry, no second page (spec §F2a asks the planner to check, and politeness is the cache window rather than the string — `data/news/__init__.py:28`):

```
GET https://www.rotowire.com/soccer/lineups.php
HTTP 200 · 462,188 bytes · text/html; charset=UTF-8
```

The markup is *kinder* than Fantasy Football Scout's, and it is stable, semantic and shallow — the same regex posture the FFS parser already takes will reach all of it:

| Thing | Where it lives |
| --- | --- |
| One fixture | `<div class="lineup__box">` — 10 on the fetched page |
| Club, full name | `<div class="lineup__mteam is-home">` / `is-visit` — e.g. `Nottingham Forest`, `Brighton & Hove Albion` |
| The two team sheets | `<ul class="lineup__list is-home">` / `is-visit` |
| Confidence | `<li class="lineup__status is-expected">Predicted Lineup` (an `is-confirmed` variant exists) |
| A player | `<li class="lineup__player">` with `<a title="Kjell Scherpen" href="/soccer/player/kjell-scherpen-29845">` |
| Position | `<div class="lineup__pos">GK\|DL\|DC\|DMC\|…</div>` |
| Where the XI ends | `<li class="lineup__title is-middle">Injuries</li>` |
| Availability tag | `<span class="lineup__inj">OUT\|QUES\|SUS</span>` |

Four consequences the plan is built on:

1. **No FPL photo codes.** FFS's fast path — the code lifted out of `/photos/players/…/{code}.png` — has no equivalent here. Every RotoWire row goes through `normalize.match_codes` and is therefore subject to `NEWS_MIN_COVERAGE`. That is the correct posture for a source that cannot self-identify, and it is why A7 keeps RotoWire out of the absence rule.
2. **The page is not Premier-League-only.** The fetch returned Ipswich Town, Coventry City and Hull City alongside the twenty — cup ties and other competitions in one list. This needs no new mechanism: the club-heading guard `fetch_lineups` already applies (`lineups.py:261-268`) drops any section whose club string `club_code` cannot resolve, and `normalize.CLUB_ALIASES` already carries `afc bournemouth`, `brighton & hove albion`, `nottingham forest`, `tottenham hotspur`, `manchester united`, `newcastle united` and `leeds united` — every long-form spelling on the fetched page.
3. **`OUT`/`SUS` → `out`, `QUES` → `doubt`**, which is exactly `ABSENCE_SLOTS`' existing vocabulary and needs no new mapping table.
4. **A player can appear twice** — in the pitch list carrying `lineup__pos red` + `QUES`, and again under `Injuries`. He resolves to `start` and `doubt`, and `fetch_lineups`' existing `sort_values("p_start_hint").groupby("code").head(1)` takes the pessimistic one. The behaviour the merge needs is already in the file.

**No alternative source is needed and none is planned.** The saved page is *not* committed — Task 4's fixture is a hand-trimmed two-fixture excerpt written inline in the test file, for the reason every other parser test in this repo gives: a 460KB asset is not a readable failure message.

### A6 — F2a takes a new Config key, 48 → 49, and the reason is a failure mode this cycle creates.

Spec §F2a asks for the key only if `[news] lineups` will not do. It will not, and the argument is short.

Today's degradation contract covers a source going **silent** — a dead host, a rewritten page, a coverage miss — and `[news] lineups = false` is a perfectly good kill switch for that, because a silent source already degrades to the flags-only path on its own. What it does not cover is a source going **wrong**: parsing cleanly, resolving above the coverage floor, and producing hints that are false. Before v10 that risk is one source's and the switch turns it off. After v10 there are two sources merged by *pessimism* (`min p_start_hint`), which means a wrong provider can only ever pull hints **down** — it can bench a real starter, and it cannot be silenced without also silencing the provider that is working.

Creating a failure mode whose only remedy is to turn off the whole feature is not a trade worth one saved config field.

```python
news_lineup_providers: list[str] = field(
    default_factory=lambda: list(DEFAULT_LINEUP_PROVIDERS))
```

parsed from `[news] lineup_providers`, defaulting to `["ffs", "rotowire"]`. Names it does not recognise are dropped with a printed line rather than raising — a typo in a TOML file must not take advice down. An **empty** list is the per-source kill taken to its limit and behaves exactly like `lineups = false`: `fetch_lineups` returns the empty frame and the flags-only path serves. `[news] lineups = false` still short-circuits everything in `advise.py:351` before this key is ever read, so the two switches compose in the only order that makes sense.

Type note, since this is the second list-valued field: `bench_curve` is `list[float] | None` and is read straight through; this one is `list[str]` with a `default_factory`, never `None`, so no caller has to test for it.

### A7 — RotoWire supplies hints only. It does not drive the absence rule, and that is a scope cut with a reason.

`notable_absences` (`lineups.py:160`) damps a regular starter who is *missing* from a parsed XI. Its safety comes entirely from `XI_SIZE`: the rule only fires for a club whose whole eleven came back **resolved**, because "the parser failed to reach him" and "the journalist left him out" are indistinguishable otherwise, and the first must never be read as the second.

For FFS that guard is cheap and strong — the codes come out of photo URLs, so a resolved XI really is eleven identified players. For RotoWire every name goes through `match_codes`, so a club's XI resolves to eleven only when eleven *name matches* succeed; a single unmatched name silently drops the club below `XI_SIZE`, and — worse — a *wrong* match puts a player in the XI who is not in it and pushes the man he displaced into "omitted", damping a starter on a matcher error.

So `Provider.absence_capable` is `True` for `"ffs"` and `False` for `"rotowire"`, `notable_absences` runs per-provider over capable providers only, and this paragraph goes in the provider's docstring. The next cycle can lift it once the match rate has a season of evidence behind it — which the coverage line the fetcher already prints will supply.

The registry is technically workable — `write_shadow` and `serving_config()` are both precedents for reading state `advise.py` cannot forward, and v9d §2's single-process contract removes the thread-safety objection. It is rejected anyway, for two reasons that do not go away:

1. **`web/routers/drafts.py:158` and `calibrate_decisions.py:97` call `solve_plan` without ever calling `ep_matrix`.** In a long-lived server process a draft re-solve would silently pick up whichever advise run last populated the registry. A2's all-or-nothing coverage rule blunts this — a horizon that does not fully match falls back — but "blunts" is not "prevents", and a *partially* stale registry that happens to cover the pool is exactly the bug nobody would find.
2. It is action at a distance in a codebase whose standing style is that a solve is a pure function of `(pool, state, kwargs)`. `serving_config()` reads an immutable file; this would read the residue of an earlier computation.

**So this plan does not plan an `advise.py` edit and does not plan a registry.** It builds the whole of §F1 as an explicit, tested, default-off keyword — `solve_plan(..., p_play=...)` — so that whichever wiring the orchestrator authorizes, the optimizer is finished and railed. Task 10 is the STOP that puts the three options and the recommendation in front of the orchestrator.

**What this costs, stated plainly:** gate **G2** (the replay) measures the *shipped* path through `backtest.py`, so until a caller is wired G2 measures nothing and its expected result is a pure seed-noise delta. Gate **G3** is unaffected — Task 11's counterfactual driver calls `solve_plan(..., p_play=...)` **directly**, so the decision change is measurable this cycle regardless of what Task 10 decides. G3 is therefore the gate that actually judges §F1, and Task 12's G2 is a no-regression check on the seed spread.

### A9 — §F1a is inert unless `bench_curve` is configured, and the replay must be checked for it.

`solve_plan:177` declares the bench-slot indicators "only when a curve is in play so the default problem is byte-identical to the pre-v4c one", and `Config.bench_curve` defaults to `None` (`config.py:57`). With no curve there are no slots and §F1a's outfield weights have nothing to scale — only the reserve keeper's term (`milp.py:289`) and §F1b and §F1c would still bite.

The machine this cycle runs on **does** configure it — `config.toml` `[optimizer] bench_curve = [0.21, 0.06, 0.002]`, `vice_weight = 0.1` — so §F1a is live here. But `replay_pair.sh` symlinks that same `config.toml` into both worktrees, which means the check is cheap and belongs in Task 12's STOP as a preflight rather than in a post-mortem:

```bash
grep -n "bench_curve" config.toml   # must print the three weights
```

A replay run with `bench_curve` unset would produce a G2 delta that is genuinely all noise, and reading that as "F1a is harmless" would be a false negative.

### A10 — §F2b joins the presser log rather than growing a column on `comp`, because `apply_availability` drops the verdict.

Spec §F2b wants `presser_log.would_factor`'s output in the news-shadow parquet. The obvious route does not exist: `apply_availability` returns `out.drop(columns=[...] + news_cols)` (`availability.py:~168`), so `llm_verdict` is gone by the time `predict_components` builds `comp`, and `advise.py:408-414` names the carried columns explicitly and is protected.

The route that does exist is better anyway. `write_presser` already banks `(season, gw, code, verdict, confidence, p_play_before, p_play_would)` — and it runs *inside* `apply_availability`, which `predict_components` (`advise.py:585`) calls before `write_shadow` (`advise.py:586`). The verdicts for this run are on disk before the shadow row is written. So:

- `news_shadow.shadow_rows` gains one column, `p_play_presser` = `p_play_news × would_factor(verdict)`, joined from `load_presser_log()` on `(season, gw, code)` and defaulting to `p_play_news` where no verdict exists.
- `SHADOW_COLS` grows by one. `write_shadow` already reindexes existing parquets that lack a column (`news_shadow.py:96-97` does it for `season`); the same treatment covers this one, so a log banked before v10 reads back fine.
- `score_news_shadow` scores a third side, `brier_presser`, **only when the column is present and is not identical to `p_play_news`** — an all-`1.0` factor is the classifier having said nothing, and a third line in the readout that is a copy of the first is worse than no line.

The presser log is instrumentation and `would_factor` never raises, but the join can still fail on a corrupt parquet: the whole join sits inside `write_shadow`'s existing `try`, and a failure leaves the column equal to `p_play_news`. Instrumentation does not block advice, and it does not block *other* instrumentation either.

**No web schema change** (`web/schemas.py:919`'s `NewsShadow`). The N2 readout the UI renders keeps its exact shape; the presser numbers are a CLI-only third line, which is what §F2b's "score it once rows accrue" asks for and what keeps this cycle's frontend diff empty.

### A11 — §F3a's bar names a metric the codebase does not compute, so the driver computes it — from the same fit.

Spec §F3a: "ship only if starters-slice `p_start` log-loss improves ≥ 1% with zeros RMSE not worse". `evaluate_benchmark` returns neither: its payload is `stratified.{all,starters}` of *EP-vs-points* metrics, and `p_start` appears only in `evaluate_current`'s holdout heads (`evaluation.py:410`).

Three things settled:

1. **The slice** is the house one — `minutes >= STARTER_MINUTES` (60), the same filter `evaluate_benchmark:1072` and `evaluate_current:384` use. Truth is `evaluation.start_truth(rows)`, which reads `starts` where the feed recorded it and infers `minutes >= 60` where it did not.
2. **The metric is nearly degenerate on that slice and the guard is what saves it.** On rows where the player started, truth is almost always 1.0, so the log-loss reduces to `-mean(log p_start)` — a confidence score, gameable by predicting 1.0 everywhere. The zeros-RMSE guard is precisely what makes that gaming unprofitable: an arm that calls everyone a starter inflates EP for the players who did not play, and the zeros stratum is where that lands. The bar as written is coherent *because* of its second half, and the driver prints both numbers on every line so the pair is always read together. The whole-frame `p_start` log-loss is printed as a companion.
3. **Both numbers come from one fit per arm.** Calling `evaluate_benchmark()` and then re-fitting for the modes would be two fits — and, worse, would compare a log-loss from one model against a zeros RMSE from another. Task 1's driver therefore runs `evaluate_benchmark`'s loop itself (`benchmark_split` → `train_all` → per-gameweek `predict_components_simple`/`assemble_ep`/`ep_matrix`), capturing `predict_modes` alongside, and calls the shipped `stratified_metrics`, `log_loss` and `start_truth` for the arithmetic. Nothing is re-derived; only the loop is re-walked.

### A12 — §F3a's lever guard is three assertions, because v9c's zeros had three ways of happening.

"The driver must raise on identical arms" (spec §F3a) is not one check. v9c's run-2 zeros came from a lever that was *bound* rather than read; v8a's `f2_league`/`f2_cups` tie came from two different feature lists that were **value-identical on the window**. Both would print a clean, believable, meaningless negative. So, before any number is reported:

1. **The lists differ.** `set(arm_features(name)) != set(arm_features("baseline"))` for every non-baseline arm.
2. **The columns exist and vary.** Each arm column is present in the memoised training frame, has at least one non-null value, and has `nunique() > 1`. A constant column is a column LightGBM will never split on.
3. **The fit read them.** After `train_all`, the arm's columns appear in `models["minutes"].feature_cols` (`minutes.py:162`). This is the assertion v9c did not have: `MINUTES_FEATURES` is read as a module global by `train_all`, so setting `tr.MINUTES_FEATURES` really is the whole intervention — but "really is" is exactly the kind of claim that stopped being true once before.

Any failure is `SystemExit` with the reason, before a single arm is scored. This is the same posture `scripts/v9d_club_eval.py:689` takes and for the same reason.

"""Gate G1, §F3a: the SHRUNK_MODE_FEATURES arm on the 2024-25 benchmark.

``shrunk_start_rate`` and ``shrunk_min_per_app`` (engineer.py:1043) were built
in v5 and no head has ever claimed them. v5's gate N1 measured them, but it
measured them *bundled with congestion* — zeros RMSE 1.082-1.084 against
1.069-1.073 — and attributed the regression to the congestion half, whose cup
archive holds no rows at or before 2024-25 and is therefore partly a season
indicator on this window (train.py:66-72). The two halves were never
separated. This separates them: the arm is the mode rates alone, on a
benchmark the confounder is not in.

The pre-registered bar (spec §F3a), against the *control arm of this same
run* and never against a banked number:

    KEEP iff  starters-slice p_start log-loss improves by >= 1% (relative)
              AND zeros RMSE does not get worse by more than GUARD_TOLERANCE.

Both numbers come from **one fit per arm**. Calling ``evaluate_benchmark`` for
the RMSE and re-fitting for the modes would compare a log-loss from one model
against an RMSE from another, so the benchmark's own loop is re-walked here
with ``predict_modes`` captured alongside. Every piece of arithmetic is the
shipped one: ``benchmark_split``, ``train_all``, ``predict_components_simple``,
``assemble_ep``, ``ep_matrix``, ``stratified_metrics``, ``log_loss``,
``start_truth``, ``STARTER_MINUTES``.

house definition. On it, truth is almost always 1.0, so the log-loss is close
to ``-mean(log p_start)`` — a confidence score, and one an arm could game by
calling everyone a starter. The zeros guard is what makes that unprofitable:
an arm that does it inflates EP for the players who did not play, and that

**The lever guards (plan A12).** Three, all before any arm is scored, because
this repo has produced a clean meaningless negative twice — v9c's rebound
lever that was bound rather than read, and v8a's f2_league/f2_cups pair that
were two lists with identical values on the window. The driver raises rather
than printing a decorated zero.

Run it, watch it, read the verdict::

    mkdir -p logs && caffeinate -i nohup .venv/bin/python \\
        scripts/v10_shrunk_arm.py > logs/v10_shrunk_arm.log 2>&1 &
    grep -e V10_ARM_DONE -e V10_VERDICT -e V10_ARM_LEVER logs/v10_shrunk_arm.log

For scale: v8a's baseline on this benchmark was zeros 1.066 / haulers 5.179 /
all 1.968 over 16279 zeros rows. That is a sanity range for the control arm,
not a comparison for the arm — CONVENTIONS §1, and scripts/replay_pair.sh's
own header, on why a banked number from an earlier cycle is not evidence.
"""

from __future__ import annotations

import json
from pathlib import Path

import pandas as pd

import gaffer.evaluation as ev
from gaffer.features.engineer import SHRUNK_MODE_FEATURES
from gaffer.models import train as tr

LOGLOSS_MIN_RELATIVE_GAIN = 0.01
"""Spec §F3a's "improves >= 1%", read as a *relative* improvement.

Absolute would be the wrong scale: a log-loss on a near-degenerate slice sits
around 0.1-0.3, and 0.01 absolute there is a 5-10% move that no feature pair
is going to make. Relative is what "1%" means about a loss.
"""

GUARD_TOLERANCE = 0.005
"""v8a's guard, reused unchanged (scripts/v8a_arms.py:36). "Zeros RMSE not
worse" with no tolerance at all would withdraw an arm on the fourth decimal
of solver noise."""

ARMS: dict[str, list[str]] = {
    "baseline": [],
    "shrunk_modes": list(SHRUNK_MODE_FEATURES),
}
"""One arm, one control. The two columns go in as a block because they are one
claim measured two ways — the same treatment v8a gave ``f2_cups`` — and
because a withdrawal here is a withdrawal of the claim, not of a column."""

_cached = None
_real_load = tr.load_training_frame


def _memoised():
    """One ``load_training_frame`` for the whole run, handed out as copies.

    The frame is the expensive half and cannot differ between arms by
    construction; copies mean an arm that mutates its frame cannot poison the
    next one. ``scripts/v8a_arms.py:53-67``, verbatim in intent.
    """
    global _cached
    if _cached is None:
        _cached = _real_load()
    df, tg, elo = _cached
    return df.copy(), tg.copy(), elo


def arm_features(name: str) -> list[str]:
    """The feature list this arm trains the minutes model on."""
    return list(tr.MINUTES_FEATURES) + list(ARMS[name])


def check_lever(df: pd.DataFrame) -> None:
    """Plan A12. Raises rather than reporting a decorated zero."""
    base = set(arm_features("baseline"))
    for name, cols in ARMS.items():
        if name == "baseline":
            continue
        if set(arm_features(name)) == base:
            raise SystemExit(
                f"the lever is disconnected: arm {name!r} builds the same "
                f"feature list as the control, so both sides would fit the "
                f"same model and every number below would be a zero with a "
                f"name on it.")
        for col in cols:
            if col not in df.columns:
                raise SystemExit(
                    f"{col} is not on the training frame — feature_columns() "
                    f"lists it (engineer.py:853) but load_training_frame did "
                    f"not produce it, so the arm would fail at fit time or, "
                    f"worse, silently drop it.")
            series = pd.to_numeric(df[col], errors="coerce")
            if not series.notna().any():
                raise SystemExit(f"{col} is entirely null on this window.")
            if series.nunique(dropna=True) <= 1:
                raise SystemExit(
                    f"{col} is constant on this window — LightGBM will never "
                    f"split on it and the arm is the control by another name.")
    print("V10_ARM_LEVER ok", flush=True)


def run_arm(name: str) -> dict:
    """One fit, then the benchmark's own walk, with the modes captured.

    Deliberately a re-walk of ``evaluation.evaluate_benchmark``'s loop rather
    than a call to it: the gate needs a p_start log-loss and a zeros RMSE off
    the *same* fitted model, and the shipped function returns only the second.
    Every number is computed by shipped code; only the loop is re-written.
    """
    from gaffer.assets import load_bootstrap_sample
    from gaffer.data.bootstrap import scoring_table
    from gaffer.models.assemble import apply_calibration, assemble_ep, ep_matrix
    from gaffer.models.train import predict_components_simple, train_all

    df, tg, _ = _memoised()
    train_df, test_df = ev.benchmark_split(df, ev.BENCHMARK_TRAIN_MAX_IDX,
                                           ev.BENCHMARK_TEST_IDX)
    train_tg, _ = ev.benchmark_split(tg, ev.BENCHMARK_TRAIN_MAX_IDX,
                                     ev.BENCHMARK_TEST_IDX)
    models = train_all(train_df, train_tg.dropna(subset=["elo_diff"]),
                       save=False)

    # Guard 3: the fit actually read the arm's columns.
    fitted = list(getattr(models["minutes"], "feature_cols", []))
    for col in ARMS[name]:
        if col not in fitted:
            raise SystemExit(
                f"arm {name!r} set MINUTES_FEATURES but the fitted model's "
                f"feature_cols does not contain {col} — the module global is "
                f"no longer the whole of the intervention (v9c's lesson).")

    scoring = ev.benchmark_scoring(scoring_table(load_bootstrap_sample()))
    ep_parts, mode_parts = [], []
    for gw in sorted(int(g) for g in test_df["gw"].dropna().unique()):
        rows = test_df[test_df["gw"] == gw].reset_index(drop=True)
        if rows.empty:
            continue
        comp = predict_components_simple(models, rows)
        ep = ep_matrix(apply_calibration(assemble_ep(comp, scoring),
                                         models.get("calibration")))
        truth = rows.groupby(["code", "gw"], as_index=False).agg(
            total_points=("total_points", "sum"), minutes=("minutes", "sum"))
        ep_parts.append(ep.merge(truth, on=["code", "gw"], how="inner"))
        modes = models["minutes"].predict_modes(rows)
        mode_parts.append(pd.DataFrame({
            "p_start": pd.to_numeric(modes["p_start"], errors="coerce").values,
            "minutes": pd.to_numeric(rows["minutes"], errors="coerce").values,
            "started": ev.start_truth(rows).values}))
        print(f"{name} gw{gw}: {len(ep_parts[-1])} rows", flush=True)

    scored = pd.concat(ep_parts, ignore_index=True)
    heads = pd.concat(mode_parts, ignore_index=True)
    starters = heads[pd.to_numeric(heads["minutes"], errors="coerce")
                     .fillna(0.0) >= ev.STARTER_MINUTES]
    table = ev.stratified_metrics(scored["ep"], scored["total_points"])
    return {
        "zeros": table["zeros"]["rmse"],
        "zeros_n": table["zeros"]["n"],
        "all": table["all"]["rmse"],
        "p_start_ll_starters": round(
            float(ev.log_loss(starters["p_start"], starters["started"])), 5),
        "p_start_ll_all": round(
            float(ev.log_loss(heads["p_start"], heads["started"])), 5),
        "starters_n": int(len(starters)),
        "rows": int(len(heads)),
    }


def verdict(base: dict, arm: dict) -> dict:
    """The pre-registered rule, applied to the arm against the control."""
    b, a = base["p_start_ll_starters"], arm["p_start_ll_starters"]
    gain = (b - a) / b if b else 0.0
    zeros_cost = arm["zeros"] - base["zeros"]
    keep = gain >= LOGLOSS_MIN_RELATIVE_GAIN and zeros_cost <= GUARD_TOLERANCE
    return {"logloss_relative_gain": round(gain, 5),
            "zeros_cost": round(zeros_cost, 5),
            "decision": "keep" if keep else "withdraw"}


def main() -> None:
    tr.load_training_frame = _memoised
    shipped = list(tr.MINUTES_FEATURES)
    df, _tg, _elo = _memoised()
    check_lever(df)
    results: dict[str, dict] = {}
    try:
        for name in ARMS:
            tr.MINUTES_FEATURES = arm_features(name)
            results[name] = run_arm(name)
            print("V10_ARM_DONE", name, json.dumps(results[name]), flush=True)
    finally:
        tr.MINUTES_FEATURES = shipped
        tr.load_training_frame = _real_load

    v = verdict(results["baseline"], results["shrunk_modes"])
    print("V10_VERDICT shrunk_modes", json.dumps(v), flush=True)
    Path("reports").mkdir(exist_ok=True)
    Path("reports/v10_shrunk_arm.json").write_text(
        json.dumps({"arms": results, "verdict": v}, indent=1))


if __name__ == "__main__":
    main()

def _frailty(dnp_rate: float) -> float:
    """A did-not-play rate -> a clamped multiplier on a population weight."""
    lo, hi = FRAILTY_CLAMP
    return min(max(dnp_rate / POPULATION_DNP, lo), hi)


def _p_play_lookup(pool: pd.DataFrame, state: SolveInput,
                   p_play: dict | None) -> dict[int, dict[int, float]] | None:
    """The §F1 gate: a usable ``{code: {gw: p}}``, or ``None`` for "don't".

    ``None`` — and therefore the pre-v10 solve, exactly — in three cases, and
    plan A2 is why each of them is a case:

    * nothing was passed, which is every caller in the tree today;
    * **coverage is incomplete** — some ``(code, gw)`` of the filtered pool
      times the horizon is missing, or is not a finite number in ``[0, 1]``.
      All-or-nothing on purpose: a pool where half the players have a
      probability and the other half are silently treated as nailed-on is the
      one failure that actively misleads, so a partially-wired caller fails
      closed;
    * the values have **no spread**. Uniform is not information, and taking
      the fast exit here is what makes "identical ``p_play`` across the pool is
      decision-identical to main" true at *any* value rather than at one.
    """
    if not p_play:
        return None
    codes = [int(c) for c in
             pool.loc[~pool["code"].isin(state.locked_out), "code"]]
    out: dict[int, dict[int, float]] = {}
    lo = hi = None
    for c in codes:
        per_gw = p_play.get(c)
        if per_gw is None:
            return None
        row: dict[int, float] = {}
        for g in state.gws:
            v = per_gw.get(g)
            # A number, and not a bool, and not a string that happens to
            # parse. A caller that built this dict out of strings built it
            # wrong, and coercing would hide that rather than fail closed.
            if isinstance(v, bool) or not isinstance(v, (int, float)):
                return None
            v = float(v)
            # NaN fails this comparison too, which is the point.
            if not 0.0 <= v <= 1.0:
                return None
            row[g] = v
            lo = v if lo is None else min(lo, v)
            hi = v if hi is None else max(hi, v)
        out[c] = row
    if lo is None or hi - lo < P_PLAY_MIN_SPREAD:
        return None
    return out


def _decision_scales(plan: "Plan", pool: pd.DataFrame,
                     pp: dict[int, dict[int, float]]) -> dict:
    """Pass one's answer -> pass two's weights and pins (plan A1).

    Three ratios per gameweek, all over the same denominator and through the
    same clamp: the XI's mean frailty for the outfield bench slots, the *XI
    keeper's own* for the reserve keeper — he plays exactly when that one man
    does not, which is why the outfield mean would be the wrong number — and
    the captain's for the vice hedge.

    The XI and the captain are pinned. The vice scale is the captain's
    frailty, so leaving the armband free in pass two would let the solver
    re-elect a captain under a weight computed from a different one; §F1
    changes no captaincy term, so pinning costs nothing it wanted.
    """
    pos = dict(zip(pool["code"], pool["position"]))
    bench_scale: dict[int, tuple[float, float]] = {}
    vice_scale: dict[int, float] = {}
    fixed_xi: dict[int, list[int]] = {}
    fixed_captain: dict[int, int] = {}
    for gp in plan.gw_plans:
        t, xi = gp.gw, list(gp.xi)
        dnp = [1.0 - pp[c][t] for c in xi if c in pp and t in pp[c]]
        if not dnp:
            continue
        out_f = _frailty(sum(dnp) / len(dnp))
        keeper = next((c for c in xi if pos.get(c) == "GKP"), None)
        gk_f = (_frailty(1.0 - pp[keeper][t])
                if keeper is not None and keeper in pp else out_f)
        cap = gp.captain
        bench_scale[t] = (out_f, gk_f)
        vice_scale[t] = (_frailty(1.0 - pp[cap][t]) if cap in pp else 1.0)
        fixed_xi[t] = xi
        fixed_captain[t] = int(cap)
    return {"bench_scale": bench_scale, "vice_scale": vice_scale,
            "fixed_xi": fixed_xi, "fixed_captain": fixed_captain}
