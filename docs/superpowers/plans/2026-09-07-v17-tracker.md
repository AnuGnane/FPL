single-flight runner could only 409. It now shares an in-flight promise inside
`useJob.ts` and caches nothing. If you add a URL to `usePageData`, ask first
whether its answer is an artifact or a fact about right now. Second, **a write
is not the only thing that staleness comes from**: a job on one hub can
rewrite an artifact another hub holds — `refresh-data` and `field-scrape`
rewrite what `/api/players` and `/api/news/{gw}` serve, and their buttons are
on Model while the readers are on This Week. `api/invalidation.test.tsx`'s
`TABLE` covers both classes and its docstring says so; add a row when you add
a writer. Third, the source-scan half of that rail matches file text with
comments stripped, so it cannot see a call on the wrong branch or after an
early return — that is why the guarded `SettingsTab` case has two behavioural
tests, and why the rail keeps both instruments. Fourth, **the Python ledger
was under-recorded**: rows through v17g say 4386, `pytest --collect-only -q`
says **4425**, and nothing deselects by default.

**Process lessons, and one mistake.** The mistake is mine and it is worth not
repeating: I ran two implementers concurrently in the same worktree, and one's
`git rm` was swept into the other's commit by the shared index — the end state
was correct, the attribution is not. **One committing agent at a time**;
read-only reviewers may overlap freely, and doing so kept the pipeline full.
What worked: giving every implementer an explicit "where your judgement is
wanted" section rather than only instructions — the plan's own `usePageData`
sketch had two real bugs (a stale in-flight answer overwriting a body fetched
after an invalidate; a path change painting the old URL's body) and the
implementer found both because it was told the sketch was not sacred. And
mutation testing is now the house default for a new rail: it caught four
assertions across this cycle that could not fail at all, including one whose
test name advertised a field it never touched. The spec's §5 table I wrote by
reading the code had a wrong row and a missing class; both were found by
telling the reviewer to rebuild the sweep from scratch rather than check mine.
