## Ambiguities the spec left open, and how this plan settles them

Sixteen. Three of them are findings rather than decisions: one place where the tree already does what §F1a asks (A1), one quantity §F2c describes that the endpoint it names does not have (A9), and one existing test that this cycle's writer is on a collision course with (A11).

### A1 — §F1a's squad column already exists end to end, and adding a second one would be the mistake.

The spec says the squad rows gain top-10k EO "served via `latest_field_eo`". They do — through a path already in place:

- `routers/players.py:148-151` reads `latest_field_eo()` under a blanket `except`, `:170` looks it up as `field_eo.get(int(r.element))` **off the snapshot row itself**, and `:171-173` classifies it with `field_class(code in owned, ...)` where `owned = state.owned_codes` (`:139`).
- `schemas.py:405-412` declares both on `PlayerRow`; `types.ts:214-215` mirrors them.
- `ThisWeek.tsx:43` fetches `/api/players` behind the advice, `:108` builds `byCode`, and `:127-128` already reads `row?.ownership` and `row?.league_eo` off it into the squad row.

So the ownership set the explorer classifies against **is the squad**, which is exactly the set `field_class` needs to distinguish a shield from a threat. A serve-time squad-row field would be a second answer to one question, drawn on one page, from one log, and the two would diverge the first time a decoration and a router disagreed about who is owned.

**Settled: §F1a's row half is two lines in `ThisWeek.tsx`'s row builder** — `fieldEo: row?.field_eo ?? null`, `fieldClass: row?.field_class ?? null` — and a column in `SquadTable`. Zero backend diff for that half. The server-side work in §F1a is the captain sentence, which is a different quantity (A2).

Note the local convention this crosses: `:127-128` uses `NaN` for a missing numeric and `fmtNum` renders that as an em dash. `field_eo`'s own contract is stricter — `types.ts:212-213`, "**Never 0 for 'unknown'**" — and `NaN` would flow into a tint comparison as a silent false. The new fields follow the v9a identity trio's `?? null` convention at `:138-140` instead.

### A2 — the captain sentence is a fourth serve-time decoration, in a new module, and it is genuinely served because of the ±SE.

`/api/players` carries `field_eo` and no `se`. The spec asks the captain framing to carry "the captain's field EO with its ±SE", and the standard error is in the log (`FIELD_EO_COLS`, `field.py:48`) and comes back from `latest_field_eo` (`field.py:231-233`) and stops at the explorer's schema. Rebuilding it client-side is impossible; widening `PlayerRow` with an `se` nobody else wants is a column on every one of ~700 rows to serve one sentence.

**Settled: a new `src/gaffer/web/field_frame.py`, modelled line for line on `web/identity.py`, exporting `with_field_frame(payload, gw) -> dict`,** composed outermost at `routers/advice.py:176-177`:

```python
payload = with_field_frame(
    with_attacking_haul(
        with_identity(with_positions(load_advice(gw), state.pool), gw)),
    gw)
```

Outermost because it reads `captain` after `with_positions` has filled it and after `with_identity` has named the club — the sentence says which club, and re-deriving that would be a second identity join.

It inherits identity's four contracts verbatim, because they are the reason that module has never taken a page down: **nothing here raises** (module docstring, `identity.py:20-23`); the payload is copied, not mutated (`identity.py:349`, `:343`); every failure returns the payload *undecorated*; and `gw` comes from the caller rather than off the payload (`identity.py:318-321`).

It adds **exactly one top-level key, `captain_field`**, and — the part that makes §Gates' byte-identity rail literal — **when there is nothing to say the key is absent, not `None`.** A `None` would be a new key on every payload on every clone that never ran a scrape, and the rail "empty field log → payload byte-identical to today" would have to be written as "byte-identical except for one null", which is the shape of an assertion that gets loosened later.

`captain_field` carries the numbers *and* the sentence:

```python
{"code": 411, "eo": 62.4, "se": 2.8, "n": 300, "gw": 2,
 "field_class": "shield",          # or "sword", or None
 "most_captained": {"code": 411, "name": "…", "gw": 2},   # §F1b, optional
 "note": "The top 10k have 62.4% ± 2.8 of him — he is cover, not attack."}
```

The sentence is built server-side because it is a *claim about the data's meaning* and the tree's standing position is that such claims are made once, where the data is (`with_attacking_haul`'s docstring, `routers/advice.py:133-138`, is the same argument about a label). The client renders `captain_field.note` and formats nothing.

### A3 — the mapping goes **code → element**, and it is guarded three ways, none of them positional.

The hazard §Gates names ("a field log with unknown elements maps to nothing, never to the wrong player") is real and it is three separate hazards wearing one coat.

The advice payload speaks `code`. The EO log speaks `element`, and `field.py:49-52` says why in so many words: *"``element``, not ``code``: the sample is picks straight off the API and a pick names a season-scoped element. Joining to ``code`` is the reader's job (``players.parquet`` carries both)."* The direction needed is therefore **code → element**, which in this tree exists exactly once, private to another router: `league_sim.py:223-235 _elements_by_code()`. (`journal.py:114` and `review.py:67` go the other way, and `journal` is import-only.)

The spec points at that helper, and this plan **does not import it**. Two reasons, both about the seam rather than the code: it is a module-private function on a router that models rival squads, so importing it would couple This Week's captain line to the league simulator's lifetime; and it re-reads `live/players.parquet` on every call, where `field_frame` needs the mtime-keyed memo `identity._memo` already provides. `field_frame` builds its own, in the same shape and with the same failure semantics, and the duplication — two code→element maps in one tree — is recorded as a residual rather than resolved by a refactor that would touch a router this cycle otherwise never opens.

**Settled — the three guards, all in `field_frame.py`:**

1. **Both columns come off the same snapshot row.** `dict(zip(players["code"], players["element"]))` over `live/players.parquet`, never an index, never a position, never a reindex. This is `league_sim.py:227`'s shape and `artifacts.py:95`'s shape. A code with no row in the snapshot yields no element, and no element yields no framing.
2. **An element the log does not carry yields no framing.** `latest_field_eo` returns a dict; a miss is a miss. Never `.get(e, 0.0)` — `schemas.py:411`'s standing sentence is the reason: *"Neither is 0.0, which the reader would take as a measured differential."*
3. **The season guard, which is the one nobody would find until it bit.** `latest_field_eo` (`field.py:225`) picks `int(frame["gw"].max())` across the *whole log*, and the log carries a `season` column it never consults. Today the file holds one season (123 rows, 2026-27 GW2, one snap day) so nothing is wrong. In August 2027 it will hold GW38 of 2026-27 and GW2 of 2027-28, `max(gw)` will be 38, and element 411 in 2026-27 is a **different footballer** from element 411 in 2027-28. That is the wrong-player failure, arriving quietly, twelve months from now.

`field.py` is unprotected, so Task 1 adds an optional `season: str | None = None` to `latest_field_eo`. `None` preserves today's behaviour byte for byte, so `routers/players.py` is not touched and not re-tested; `field_frame` passes `load_config().current_season`. The residual — that the explorer keeps the unfiltered call — is recorded in Task 13's README line rather than fixed by a drive-by edit to a shipped page.

### A4 — `advise.py`'s `captain_note` is a different sentence and is left alone.

### A5 — §F1b's `most_captained` is a live fact for the current gameweek, and a null for every week after it.

Verified against the banked bootstrap (`data/raw/bootstrap-20260830T200155.json`):

| event | finished | `most_selected` | `most_captained` |
| --- | --- | --- | --- |
| 1 | true | 411 | 411 |
| **2** | **false** | **165** | **411** |
| 3 | false | `null` | `null` |
| 4+ | false | `null` | `null` |

So it is *not* a lagging statistic, which is what a reader would assume: FPL publishes it live for the gameweek that is open, and `null` for everything beyond it. Two consequences the plan fixes now rather than discovering on a Friday:

- **The value is an element**, so it goes through A3's map and A3's guards, exactly like the captain's own EO. A `most_captained` that resolves to no code is simply absent from `captain_field`.
- **The framing names the gameweek**, because the honest sentence is "the field's most-captained player *in GW2*", and a payload served on Friday for GW3 must not print GW2's modal captain as if it were this week's. `build_events` keys rows by `gw` (`bootstrap.py:97`), so the join is on the advice gameweek and a miss is an absence.

Ingestion is **one edit**, and the asymmetry that makes it one is worth recording: `artifacts.save_snapshots` projects players through the `SNAPSHOT_PLAYER_COLS` allowlist (`artifacts.py:393`) but saves events **whole and unfiltered** (`:398`). So two keys in `bootstrap.build_events` (`:93-106`) reach `data/live/events.parquet` with no second list to update. Readers take `pen_tracker.finished_gws`' shape (`pen_tracker.py:42-52`): a column-absence guard first, so a parquet banked before this cycle is a missing column and never a `KeyError`.

### A8 — a blank is defined against the gameweeks that exist, not against 1..38.

The naive definition — "a team with zero fixtures in gameweek `t`" — makes every team blank in every gameweek the file does not describe, which on a partial fixture download is all of them. And a gameweek row-set that is entirely absent is not a league-wide blank; it is a gameweek nobody has published yet.

**Settled:** the detector considers only gameweeks **present in the frame**. Within such a gameweek, `blanks` are the teams in the season's team set with a count of zero and `doubles` are the teams with a count `>= 2`. The season's team set is the union of every team appearing anywhere in the frame — not a hardcoded twenty, because a mid-season file and a pre-season file have different unions and the constant would be right in exactly one of them.

Today's real file makes this concrete and makes the empty state the *main* case rather than a corner: **380 rows, 38 gameweeks, exactly 10 fixtures in every one, 20 teams appearing once each.** No doubles, no blanks, nothing to detect. That is the reality §F2c's honest empty state is written for, and it is why Task 11 builds the empty state first and tests it hardest.

### A9 — `/api/chips/plan` does not carry the θ the spec asks it for, and the fix is at the router because the alternative is a protected edit.

Spec §F2c: "Served numbers come from the existing `/api/chips/plan` (meta.py:49-71) plus the new outlook endpoint." Read it and it does not:

- `meta.py:69` calls `chip_plan(table, now_gw=state.gws[0])` — **`thresholds` left at its default `None`** (`optimize/chips.py:235`).
- With `thresholds=None`, `chip_plan` sets `threshold_now = None` and `play_now = None` (`chips.py:274-280`).
- And `ChipPlanRow` (`schemas.py:515-526`) **declares neither field**, so even if they were computed, `ChipPlanRow(**row)` would drop them silently — pydantic ignores extras. That is precisely v9d's `odds_blend_weight` lesson: an undeclared field never reaches the page, and nothing fails while it doesn't.
- The frontend has never fetched this route; `types.ts:118-131 ChipPlanRow` is a type with no consumer.

So the θ trajectory has to be *added*, and the obvious place — a `theta` beside `gain` in `chip_plan`'s `weeks` rows — is inside `optimize/**` and would be the cycle's only protected edit. It is not needed, because `thresholds` is a plain callable `(chip, gw) -> float` (`chip_policy.py:162-163`, `:195-196`) that the router can loop itself.

**Settled — all in `routers/meta.py` and `schemas.py`, both unprotected, no route added.** `meta.py` imports none of these today, so five names join its import block: `chip_thresholds_from_asset`, `chip_windows` and `load_chip_scenarios` from `gaffer.optimize.chip_policy`, `load_decision_priors` from `gaffer.assets`, and `load_config` from `gaffer.config`.

```python
priors = load_decision_priors() if load_config().decision_priors else None
thresholds = chip_thresholds_from_asset(priors, load_chip_scenarios())
rows = [] if table.empty else chip_plan(table, now_gw=state.gws[0],
                                        thresholds=thresholds)
for row in rows:
    row["thetas"] = [round(float(thresholds(row["chip"], w["gw"])), 2)
                     for w in row["weeks"]]
    row["window"] = list(chip_windows(state.gws[0]))
```

`chip_thresholds_from_asset(priors, load_chip_scenarios())` is `advise.py:735-736`'s expression, character for character, so the bar the Outlook draws is the bar the advise run actually solved against — not a second opinion computed a different way on the same page. `ChipPlanRow` gains `threshold_now`, `play_now`, `thetas` and `window`, all with defaults, so the existing (unused) shape still validates.

This also makes `chip_windows` a live function for the first time. Its return is `(gw, 19)` or `(gw, 38)` — note the **first element is `gw` itself, not the window's first gameweek** — so the field is documented as `(from_gw, last_gw)` and the UI renders "expires after GW19", never "window starts at".

Every temptation in review will be to emit it as `None` "for the type's sake". Refuse: the §Gates rail is plain byte-identity, and a rail with an exception in it is a rail that gets loosened.
