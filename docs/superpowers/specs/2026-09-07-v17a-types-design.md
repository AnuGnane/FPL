of the v17 deepening programme
(`docs/superpowers/plans/2026-09-07-v17-deepening-programme.md`, card `#c6`

`Config` field.*

## 0. Why

The step that writes `frontend/src/types.generated.ts` has no home. What the
tree does today (2026-09-07, `main` at `980c04f`):

- `scripts/gen_types.py` writes `frontend/src/schemas.json` from the live
  pydantic models and prints "now run: cd frontend && npx vitest run
  src/types.generated.test.ts".
- `frontend/src/types.generated.test.ts` holds the only executable copy of
  the `json-schema-to-typescript` options (`OPTIONS`, six lines), compiles
  the committed schema with them and diffs the result against the committed
  `types.generated.ts`. It can say the file is stale; it cannot write it.
- The write step is a twelve-line `node --input-type=module -e` one-liner
  that re-declares `OPTIONS`, in CLAUDE.md and in three plan documents.
- Nothing checks drift on demand. A change to `schemas.py` is discovered
  stale by two suites, one Python and one vitest, each pointing at the
  other.

The review's deletion test: delete the one-liner from CLAUDE.md and the
file can no longer be regenerated by anyone who has not read the test.
That is the shallow module.

## 1. The decisions the user made

1. **The node script drives.** `frontend/scripts/gen_types.ts` owns the
   compile options, spawns the Python half, and writes or checks
   `types.generated.ts`. `npm run types` is the interface, as the programme
   put it.
2. **Node runs the TypeScript natively.** No `vite-node`, no new
   dependency. This machine's Node 26.3 ran the probe with no flag and no
   warning; the compile took 110 ms. The script header records the
   constraint (Node ≥ 22.18, where type stripping is unflagged).
3. **The vitest test imports the render function**, not the options. The
   test then diffs exactly what the writer writes, and no option is
   restated anywhere. `OPTIONS` is exported for the reader but has one
   caller.

## 2. Approach, and the two rejected

**Node drives, Python forwards (chosen).** `npm run types` runs
`node scripts/gen_types.ts [--check]` from `frontend/`. The script resolves
the repo root, runs `.venv/bin/python scripts/gen_types.py [--check]` with
inherited stdio, then reads `schemas.json`, prepends `types.banner.txt`,
compiles with `OPTIONS`, and either writes `types.generated.ts` or compares
it. Each half owns one file and reports on that file by path.

*Python drives (rejected).* `scripts/gen_types.py` would spawn node for
the compile and `npm run types` would alias it. The options would still
have to live in TypeScript for the test to import them, so the driver would
be the half that knows nothing about the options it invokes.

*npm chains both (rejected).* `"types": "python … && node …"` is the
shortest plumbing, but `npm run types -- --check` appends the flag to the
last command only; the check would need a second script, and "one command"
would be two.

## 3. The interface

### 3.1 `npm run types`

Adds `"types": "node scripts/gen_types.ts"` to `frontend/package.json`.
Run from `frontend/`:

```
npm run types              # writes src/schemas.json and src/types.generated.ts
npm run types -- --check   # writes nothing; exit 1 if either file drifted
```

Write mode prints one `wrote <path>` line per file, repo-relative. Check
mode prints one `<path> is stale — run \`npm run types\`` line per drifted
file, checks both files even when the first has drifted, and exits 1 if any
line was printed. Both halves exit 0 otherwise. An unknown argument exits 2
with a usage line. A missing `.venv/bin/python` exits 2 naming the path it
looked for; the script does not fall back to a system `python3`, because a
schema written by an interpreter without `gaffer` importable is a stack
trace and not a schema.

### 3.2 `frontend/scripts/gen_types.ts`

The module. Its exports, in the order a reader meets them:

- `OPTIONS` — the six `json-schema-to-typescript` options, `as const`. The
  only definition in the tree.
- `render(schema, banner)` → `Promise<string>` — banner plus
  `compile(schema, 'GafferApi', OPTIONS)`. Pure. The vitest test calls it.
- `main(argv)` → `Promise<number>` — the driver described in §3.1; runs
  only when the file is the entry point (`process.argv[1]` is this file).

Only erasable TypeScript syntax: no `enum`, no `namespace`, no parameter
properties, so Node's type stripping runs it unchanged. Imports use the
`node:` scheme; `json-schema-to-typescript` is imported as a library, as
the test does today.

### 3.3 `scripts/gen_types.py --check`

`main(argv)` gains one flag. `--check` compares `serialize(build_schema())`
with the committed file's bytes and exits 1 with
`frontend/src/schemas.json is stale — run \`cd frontend && npm run types\``
on a mismatch, 0 otherwise, writing nothing. Without the flag it writes as
today and prints `wrote frontend/src/schemas.json`; the "now run" hint goes,
because the command that called it is the one that runs next. `main` takes
`argv` and a `root` so the test can point it at a temporary copy. The
module docstring's flow description is rewritten for the one command.
`build_schema`, `serialize`, `RENAME`, `WIRE_ONLY`, `NARROWING_REASON`,
`OPTIONAL_ON_THE_WIRE` and `schema_path` are unchanged and the twenty rails
that import them are untouched.

### 3.4 `frontend/src/types.generated.test.ts`

Drops its `OPTIONS` and its private `generate()`; imports `render` from
`../scripts/gen_types` and calls it with the committed schema and banner.
The two cases survive as they are: "is exactly what the committed schema
compiles to" and "is deterministic". The header comment says the test diffs
what `npm run types` writes.

### 3.5 What the docs say

- `CLAUDE.md`: the *Regenerating types* subsection becomes the one command
  and its check flag, and the sentence that `schemas.json` and
  `types.generated.ts` are committed together. The node one-liner goes.
- `frontend/src/types.banner.txt`: "`npm run types` writes this file from
  `src/gaffer/web/schemas.py`; `npm run types -- --check` says whether it
  is stale". The banner is prepended to `types.generated.ts`, so the
  regenerated file carries the new text; that is the command doing its job,
  not a hand edit.
- `docs/GUIDE.md` §8's `gen_types.py` bullet becomes the `npm run types`
  bullet; §11 gains the v17a line at the end of the cycle.
- The three plan documents that quote the one-liner are records of the
  cycles that wrote them and are not edited.

## 4. What sits behind the seam

Behind `npm run types`: the interpreter path, the Python script's name and
location, the banner file, the compile library and its options, the
`'GafferApi'` root name, the order of the two writes, and the byte
comparison. A reader who runs the command needs none of them; a reader who
changes the schema learns one command from CLAUDE.md.

Adapters: two callers of `render` (the driver and the test), one caller of
the Python script (the driver, and the Python rails that import its
functions directly). The hand-written narrowings in `types.ts` are the
other seam the card names; they have a written reason per model in
`NARROWING_REASON`, are rail-checked, and are out of scope here.

## 5. Tests

Survive unchanged: the twenty rails in `tests/test_v12_w5_gen_types.py`;
the vitest drift and determinism cases (import changed only);
`types.test.ts`.

New, in `tests/test_v12_w5_gen_types.py`:

- `test_check_mode_exits_one_and_names_the_file_when_the_schema_drifted`:
  a temporary root with a copy of `schemas.json` altered by one byte;
  `main(["--check"], root=tmp)` returns 1 and the captured output names
  `frontend/src/schemas.json`; the file is unchanged afterwards.
- `test_check_mode_exits_zero_when_the_schema_is_current`: same root,
  unaltered copy; returns 0, writes nothing.
- `test_write_mode_writes_the_serialized_schema`: `main([], root=tmp)`
  writes exactly `serialize(build_schema())`.
- `test_an_unknown_argument_is_a_usage_error`: `main(["--frobnicate"])`
  returns 2, prints a usage line to stderr, writes nothing.

Die: none. The vitest test's private `OPTIONS` and `generate()` are
deleted, not tests.

The node driver's check mode is exercised by the gate, not by a test: a
vitest case that spawned the venv's interpreter would make the frontend
suite depend on the Python environment, which it does not today.

## 6. Gate (surface), stated before anything runs

Run by the orchestrator on the branch, after the suites are green. All
three must hold:

1. **Check mode sees drift and the writer clears it.** Hand-edit one line
   of `frontend/src/types.generated.ts`. `cd frontend && npm run types --
   --check` exits 1 and its output names `frontend/src/types.generated.ts`.
   Run `npm run types`; then `npm run types -- --check` exits 0 and
   `git diff --stat` is empty. Repeat once with one byte of
   `frontend/src/schemas.json` altered instead: the check exits 1 naming
   `frontend/src/schemas.json`, the writer restores it, the check exits 0,
   the diff is empty.
2. **One definition.** `.venv/bin/pytest -q tests/test_v12_w5_gen_types.py`
   and `npx vitest run src/types.generated.test.ts` pass, and
   `grep -rln bannerComment frontend/scripts frontend/src` prints exactly
   one path, `frontend/scripts/gen_types.ts`.
3. **One command in CLAUDE.md.** The *Regenerating types* subsection's
   fenced block contains one command (the check flag may appear as a second
   line of the same block), and `grep -c 'input-type=module' CLAUDE.md`
   prints 0.

Also required, not part of the verdict rule: `.venv/bin/pytest -q` and
`cd frontend && npx tsc --noEmit && npx vitest run` green, vitest's
`Errors` line absent. Screenshots: not applicable, no page changes.

Verdict: pass if all three hold on the first run after the implementation
is complete. A failure is fixed on the branch and the gate is rerun in
full; the spec's §Outcome records every run.
